# Changelog

## Unreleased

The team release: Wave 1 (#75–#90), Wave 2 (#91–#100), Wave 3 (#101–#110) and its follow-ups (#111–#113), and Wave 4 (#114–#117), one release. One hangar for a team of six at ~60 sessions, with people, team credentials and per-person caps and budgets; work from GitHub, Slack, Jira and GitHub Projects; an approval lands the PR; environments that live with the repo, with services and a computer for every agent; egress allowlists, secret scanning and short-lived cloud credentials; restarts and the nightly power cycle strand nothing, and deploys are gated; history out of memory, a rotatable vault key, agent-led environment setup, the Cloud Doctor and an operator console, and a harness canary with `balanced` models by default and `frontier` a line away; heavy development environments (Docker inside a VM of the sandbox's own, deny by default for a repo's own request, bigger profiles, warm dependency and compile caches, structured test results from every check) and three thin interfaces for the sister tool that inspects and evaluates runs (harness manifests, trace export, experiment jobs). **Upgrading a running hangar:** follow [docs/upgrading.md](docs/upgrading.md#upgrading-to-the-team-release-75117), one ordered procedure, in order.

### Replay, trials and shadows (P4)

- **The eval queue class** (#181). Jobs carry `queue_class: interactive | eval`; experiment trials are `eval`. Eval jobs start only inside `HANGAR_EVAL_WINDOW` (`20:00-00:15` in `HANGAR_EVAL_TZ`, `America/New_York`), always after waiting interactive jobs, in at most `HANGAR_EVAL_MAX_RUNNING` slots (default half), and, with `HANGAR_EVAL_TPM_BUDGET` set, only while the provider's observed rolling-minute token rate plus a typical trial's fits the budget. Held jobs stay `queued` with `reason` `eval_window`, `eval_slots` or `eval_tpm`. The power-down drain cancels running trials as `infra_error` / `power_down`, and their retries (outside the 10% outage cap) wait for the next window instead of the power-up. `GET /api/admin/eval-queue`, `POST /api/jobs/{id}/priority` (`now`, admin), and `hangar_eval_*` metrics. **Behaviour change:** an experiment submitted during the day now waits for 20:00; set `HANGAR_EVAL_WINDOW=always` for the old behaviour. [docs/team-scale.md](docs/team-scale.md#the-eval-queue-class)

### Adopt and capture (P2: #133–#171, #221; PRs #208–#215, #225–#243)

Six engineers on three repos: planned work comes in through Jira, the inbox reaches people in Slack, review load gates admission, and every run is captured for the sister tool (flightdeck). Harnesses become locked, reproducible directories.

**Behaviour changes on upgrade:**

- **Self-approval needs low risk and an independent AI review** (#160, PR #238). Repo policy `self_approval` defaults to `low_risk_with_ai_review`. With `land: auto_after_approval`, a person's own approval of their own job's PR lands it only when the packet's risk is `low` and an independent AI review of that head isn't `blocking`. Otherwise the PR waits for a second reviewer, with a `landing.note`, an audit entry `landing.self_approval` and an inbox `review` item for the repo's approvers. Team jobs and the taint gate (#130) are unchanged; `HANGAR_SELF_APPROVAL=allow_solo` with one person still lands. To keep the old behaviour: `hangar repo set <repo> --self-approval any`.
- **The 5-PR review cap is on** (#159, PR #238). Once a person has 5 open agent PRs awaiting review (`HANGAR_PERSON_MAX_OPEN_AGENT_PRS`, repo policy `max_open_agent_prs`, per-person `HANGAR_PERSON_MAX_OPEN_AGENT_PRS_OVERRIDES`), their new jobs stay `queued` with reason `awaiting_capacity` until one merges or closes. Follow-ups, auto-fix and verify-fix turns, trials and review jobs are exempt; `hangar job admit <id>` lets one through. `0` turns it off ([team-scale.md](docs/team-scale.md#review-capacity)).
- **PR body separator `___`** (#137, PR #240). Hangar's PR body sections are now separated by `___` instead of `---`, because `git interpret-trailers` reads a `---` line as the end of the message. The body ends in trailers (`Hangar-Job`, `Harness-Digest`, `Environment-Digest`, and `Harness-Lock` when thawed), and the squash or merge commit hangar lands carries them too (not with `merge_method: rebase`). Anything that splits hangar's PR bodies on `---` needs updating ([jobs.md](docs/jobs.md#the-pull-request)).
- **Plugins in the manifest change `harness_digest`** (#136, #221; PRs #215, #233). The manifest gains a `plugins` section, part of `harness_digest`. Its identity is `plugins[*].{name, marketplace, digest, enabled}`. Turns without plugins record `null` and keep their digests; any turn with a seed plugin gets a new `harness_digest`. Compare digests across the upgrade only for plugin-free turns, and re-freeze locks taken from turns with plugins.
- **Hardened turns load seed plugins** (#136, PR #215). `ask` and `deny-risky` turns used to drop every plugin. They now load the environment's read-only seed plugins (`plugins:` in the spec, baked into the image at `/opt/hangar/claude-seed`) and still drop everything else. The harness canary refuses a Claude Code version below 2.1.273 (`canary.FLOORS`).
- **Slack DMs by default** (#157, PR #229). People with a linked Slack account get immediate DMs for questions and approvals on their own work (`notify: questions`, the default) and a digest at 10:15 and 16:00 `America/New_York` on weekdays. Opt out with `hangar person set <id> --dm off`. The Slack app needs the `im:write` scope (re-apply `docs/slack-app-manifest.yaml`; `hangar doctor` warns without it). The manifest also enables interactivity, which the steer classification buttons need (#162).
- **Experiments refuse floating model aliases** (#167, PR #212). A variant whose model is `opus`, `*-latest`, an OpenRouter `~` id or similar is refused at submit, naming the concrete ids to pin. Jobs and sessions still accept aliases; every manifest records `model.concrete`.
- **Trials ended by infrastructure are retried** (#166, PR #213). A trial cut off by preemption, power-down, a rate limit, a provider 5xx, a failed sandbox create or a restart is marked `excluded` and retried with the same key, up to `HANGAR_TRIAL_INFRA_RETRIES` (2), capped at 10% of an experiment's trials.

**Harnesses as locked directories** ([docs/harness-lock.md](docs/harness-lock.md)):

- **`harness.lock` and freeze** (#133, PR #210). `hangar harness freeze <session|job> --turn N --out DIR` writes a turn's native files and `harness.lock` (`hangar.harness-lock/v1`), whose identity is that turn's `harness_digest`; `hangar harness check DIR` verifies a directory against its lock. Freeze fails, naming the gap, on a skill the agent changed, a source edited since, an unpinned git skill or a file holding a secret.
- **Thaw and turn-1 drift** (#134, #221; PRs #211, #233). `hangar harness thaw NAME@REV --env ENV`, `harness_lock` on jobs and sessions: the run is pinned to the lock's harness, concrete model and approvals, and the lock's guide, skills and plugins are mounted read-only from a content-addressed copy. Turn 1's manifest is compared with the lock (`SessionTurn.drift`, a `harness.drift` event, a packet line); `HANGAR_HARNESS_DRIFT=fail` stops the turn. `hangar harness outdated NAME` reports upstream drift.
- **Plugins from a read-only seed** (#136, PR #215). `plugins: [{path, name, marketplace?, enabled?}]` in an environment builds a Claude Code seed into the image. Hangar's `--settings` enable exactly those plugins, each turn gets a fresh plugin cache, and auto-update is off.
- **The team harness repo** (#138, PR #242). `HANGAR_HARNESS_REPO` takes a git URL (`#ref` optional) as well as a path; hangar keeps a full checkout, refreshed every 10 minutes and on a `push` webhook. `GET /api/harness-locks` lists harnesses and channels, and `hangar doctor` reports the repo. `HANGAR_DEFAULT_HARNESS` (off by default, e.g. `team-default@stable`) runs intake jobs that name no harness from that lock.
- **PRs say which harness wrote them** (#137, PR #240): the trailers above, and the review packet's Agent line links the harness digest and lock.

**Work comes in, and reaches people:**

- **Jira "Ready for agent" is the default door** (#156, PR #241). `hangar setup jira` stores the credentials and writes `HANGAR_JIRA` with `trigger.status: "Ready for agent"` and the usual statuses. Agent ticket templates are in `docs/templates/`. A ticket's acceptance criteria reach the job as an untrusted `acceptance.md`. Its verify command is used only when it matches the repo policy's new `verify_allowed` globs. Slack stays at `@hangar adr`.
- **The inbox reaches Slack** (#157, #158; PR #229). Items carry a stable `id` and native `links` (PR, ticket, thread, job). Delivery is per person: `hangar person set <id> --dm --quiet --tz --digest --digest-weekends`, or `PUT /api/people/{id}/delivery`. `HANGAR_GITHUB_APP_SLUG` scopes the digest's review-queue link.
- **Steers are classified** (#162, PR #235) as `correction`, `redirect` or `new_info`. In Slack this is a prefix or buttons, in Jira a prefix or `/hangar class`, and over REST `POST /api/jobs/{id}/turns/{n}/class`. Traces carry `hangar.steer.class` and `hangar.seq`.
- **Independent AI review** (#161, PR #238). Repo policy `ai_review: hangar | check:<name> | off` (off by default). It runs a review job on the other harness and posts one `COMMENT` review with up to 20 inline comments.
- **`hangar repo check OWNER/REPO`** (#155, PR #209). One readiness report per repo covering GitHub, repo policy, CI and branch protection, posture, gateway, sudo, logins, Jira and Slack; also `GET /api/repos/{owner}/{repo}/readiness`.

**Capture for flightdeck:**

- **The outbox** (#163, #189; PR #214). With `HANGAR_OUTBOX_URL` (`gs://…` or a local directory), every finished run is written once, redacted, as `hangar.run/v1` objects (`run.json` last, plus the manifest, trace, tests, grade and patch), along with PR lifecycle job events ([docs/api/outbox.md](docs/api/outbox.md)). `hangar outbox status|retry|backfill`. Deleting a session waits for its runs to be exported (`HANGAR_EXPORT_GRACE_DAYS`, 30; `hangar session delete --force-now`). Terraform adds the `hangar-runs` bucket, with deletes denied to hangar's service account.
- **Trusted test runs everywhere** (#164, PR #225). `counted` (`trusted`, `total > 0`, complete) is on every `test.run` event, on `/api/jobs/{id}/tests` and in `tests.json`. Grader runs become `grader` TestRuns, and session exports carry each turn's runs.
- **Per-edit tree hashes** (#165, PR #231). The driver records `git write-tree` after each changing tool, in a private git dir that runs none of the repo's config. Hashing stops for the turn if one takes over 2 s. Traces carry `hangar.git.tree*`.
- **`infra_error` outcome class** (#166, PR #213). `outcome_class` and `infra_reason` are recorded on turns, attempts, job results and trials, and on traces (`hangar.outcome.class`). Records from before read `null`.
- **Weekly metrics and the standup line** (#168, PR #239). `hangar metrics weekly` (`GET /api/metrics/weekly`), with definitions from flightdeck's metrics page ([docs/metrics.md](docs/metrics.md)), and `/hangar abandon <reason>` on PRs. A weekday standup line goes to `HANGAR_STANDUP_CHANNEL` at 10:18 New York time (off without a channel).
- **The Friday harness review** (#169, PR #243). `hangar review queue|label|status` labels the first failure of failed and abandoned jobs, up to 20 candidate tasks. Labels are exported as outbox `label` events ([runbook](docs/runbooks/harness-review.md)).
- **The governance decision point** (#171, PR #208). Spec 0015 defines how hangar will ask the governed workspace for its approvals; `governance.py` is a client skeleton with contract tests, not wired in yet.

**Internal:** the analysis boundary is written down and guarded (#147). Spec 0014 §1 gains a "What stays in hangar and why" table (the drift flag, the flaky list, per-run test counts, model ranking, admission counts and the weekly metrics, each with its flightdeck counterpart), and `tests/test_boundary.py` fails when `src/hangar/` imports a statistics library (`scipy`, `numpy`, `pandas`, `statistics`, `duckdb`, `pyarrow`) or defines an estimator-named function, pointing at the spec.

**Fixes:** `hangar doctor` no longer fails a fresh laptop install on the intake posture: without the git gateway it warns until an intake front door is configured, then fails naming those doors, with one fix command (#236, PR #247).

### The safe release (P1, #120–#132; [docs/upgrading.md](docs/upgrading.md#the-safe-release-120132))

Secure defaults before a second engineer joins. #123–#125 enforce by default and can be switched back to warn for this release only; the next release enforces.

- **Approvals: one rule on every path** (#121). MCP `approve_job`/`reject_job`, REST (`hangar job approve`), GitHub and Jira `/hangar approve|reject` all go through `approvals.decide`: an admin or a linked repo approver, over MCP/REST with a login token only (`mcp` and `jobs` tokens can't release work), and never the job's own person or requester. `HANGAR_SELF_APPROVAL=allow_solo` permits a self-approval while one person exists. Refusals are audited (`job.<decision>.refused`); `hangar doctor` warns when nobody could approve.
- **REST/MCP scope parity** (#122). `tests/fixtures/scope_matrix.yaml` lists every tool, resource and route with its scope and owner rule; `test_scope_parity.py` checks it against what the code enforces.
- **Intake posture** (#123). Jobs from GitHub, GitHub Projects, Jira, Slack and inbound webhooks (and auto-fix rounds and env setup started from an issue) need the git gateway (`HANGAR_INTAKE_POSTURE=enforce`, the default: refused at submit otherwise, with a message on the ticket or thread) and get at least `allowlist` egress, cold-starting. `warn` runs them as before with a `posture.warn` event; `deploy/k8s/config.yaml` sets the gateway, the egress proxy and `enforce` ([security.md](docs/security.md#intake-posture)).
- **sudo off by default** (#124). `EnvSpec.sudo` defaults to `false` (every environment image tag changes once); heavy environments imply `true`. Under `enforce` a job's Docker sandbox runs with `no-new-privileges`, and an intake job on a heavy environment needs the repo policy's `allow_heavy_for_intake`.
- **Subscription logins are interactive-only** (#125). Jobs, schedules, webhooks, experiments and replays refuse `oauth_token` and `auth_file` credentials before a sandbox starts, naming the `hangar cred add … --kind api_key` fix; a person's own sessions keep theirs with a warning. `HANGAR_SUBSCRIPTION_LOGINS=any` lets jobs use them with a warning, and `hangar doctor` fails ([team.md](docs/team.md#subscription-logins)).
- **Sealed graders** (#126). An experiment's grader runs with egress `none`, no credential, MCP, services or warm pool, its git grant revoked before the patch runs; hidden tests are written outside the repo (`files_mode: pristine`) and run by `hangar-grade pytest` with nothing from the patch loaded first; `grader.network: mirror` for packages; `tamper_signals` per trial.
- **Grade anti-forgery** (#127). With the uid split hangar's user owns the grade (`trust: isolated | best_effort | low`); hidden tests that pass on the base, or a reference patch that fails them, make the task `invalid_task`; a canary in every hidden test file, found in a trial's output, makes it `contaminated`.
- **Jira Automation hardened** (#128). An Automation request starts a job only within `automation_max_transition_age_minutes` (10) of the trigger transition, at most `automation_max_starts_per_issue_per_day` (3); stale, wrong-event and bad-token requests alert the admins; `hangar cred add NAME --rotate`; `hangar doctor` warns on a token older than 90 days.
- **Taint tracking** (#129). Turns, sessions and jobs record whether the agent read untrusted content (`context`, `web`, `mcp`, `file`), sticky across turns and forks; MCP servers gain `trust`; the trace export and the review packet carry it ([security.md](docs/security.md#taint)).
- **Taint gates** (#130). A tainted job's PR opens as a draft labelled `hangar:tainted`; landing it needs a person other than the job's own or its requester; egress approvals for it need an admin or a repo approver; under `ask`/`deny-risky` pushes, PRs, network commands and MCP write tools (`mcp.<name>.write_tools`) are risky. Every decision is audited as `taint.gate`.
- **Harness and environment digests** (#131). `hangar.manifest/v1` gains optional `harness_digest` and `environment_digest` (the two halves of `config_digest`, canonical form in spec 0014 §2); turn spans carry them.
- **`extends` merge rules** (#132). Component lists (`skills` among them) replace the parent's; build inputs union; `null` deletes a map key; `skills_remove` drops inherited skills, in environments and experiment variants. `hangar env migrate-merge --dry-run` reports what resolves differently.
- **A green main before a release** (#120). The background-process MCP tests are deflaked, and [docs/ci.md](docs/ci.md#release-gate) gains the release gate: the last 10 `ci.yml` runs on main green.

### A team on one hangar

- **One control plane for a team of six at ~60 sessions.** Sandbox, job and session lookups use expression indexes instead of parsing every record ever made (a team load test: `get_session` p50 3.4 s → 42 ms, event-loop lag p95 5.2 s → 70 ms). Stopped and failed sandbox records idle for 7 days move to an archive table, still found by id, never while a snapshot or a credential lease points at them. Caps per person on live sessions (15), sandboxes (20) and running jobs, counted by the person each record belongs to; a fair job queue serves whoever has the fewest jobs running. `HANGAR_MAX_SANDBOXES` goes to 120 and job slots to auto (8 on GKE; 24 by hand once budgets are set). Workspace archives in flight share a 1 GiB memory budget, so a fork can't exhaust the control plane. On GKE: `n2d-standard-16` sandbox nodes (AMD keeps SMT on under gVisor), up to 10; sandbox pods request half their CPU; `power.sh up` keeps an autoscaling range set while the cluster was down. [docs/team-scale.md](docs/team-scale.md)
- **History out of memory** (wave 3). Jobs and sessions were all loaded at startup and kept (~30 KB a finished job: 735 MB at idle with six months of a team's history in the load test); now hangar keeps live work and the last `HANGAR_RESIDENT_MINUTES` (60) and reads the rest from the store by id, name or index (213 MB in the same test; `list_jobs` p50 115 → 77–87 ms). Listings page through the store's indexes filtered by person, so a member sees all of their own work, not what was left of the team's newest 500: each item has a `cursor`, passed back for the next page (`X-Next-Cursor` on REST). Finished jobs and settled sessions untouched for 30 days move to archive tables, still found and listed, never deleted, except what is still referenced: open PRs, sessions with checkpoints, a schedule's last job. GitHub, Jira and Projects lookups, idempotent retries, the inbox, the usage report and daily caps read the store's indexes. **Upgrade note:** the first start indexes the job and session tables; before rolling back, hand archived records back ([docs/upgrading.md](docs/upgrading.md#rolling-back-this-release)). [docs/team-scale.md](docs/team-scale.md#months-of-job-and-session-history)
- **The vault key can be rotated** (wave 3; the hardening review). One key encrypted the vault, every checkpoint and every backup, with no way to replace it. `HANGAR_SECRET_KEY` (or the key file) now holds keys newest first: the newest encrypts and signs, any key not retired decrypts and checks (`MultiFernet`). `hangar admin rotate-key` re-seals the vault and the database's other sealed rows at once, re-encrypts checkpoints, artifacts and backups in a background pass that survives restarts (a checkpoint part copied meanwhile is re-encrypted as it is copied), and retires the old key once the pass is done and no sandbox from before the rotation still holds tokens of it. Keys live in Secret Manager, never in a file on a laptop (the upgrade guide used to say otherwise). `HANGAR_BACKUP_STORE` puts backups in a bucket of their own, and `hangar doctor` warns while they share the checkpoints' bucket and service account. [docs/security.md](docs/security.md#rotating-the-vault-key)
- **Repo builds pass on less, and their templates are cleaned up** (wave 3; the #99 review's Low findings). A build's `.git` no longer carries the hooks and git config `install` left (hooksPath, fsmonitor, filters, aliases, includes) into every sandbox started from it, and hangar's own git commands there run with hooks off. On Kubernetes, the reaper deletes the SandboxTemplates and warm pools made per build and per set of services once no live sandbox uses them; trimming a build's history no longer deletes a template a session still runs on. [docs/environments.md](docs/environments.md#limits-of-this-version)
- **People: one hangar for a team.** Every token belongs to a person, an admin or a member (`hangar person add|ls|role|token|rm`, `/api/people`). Members see and act only on their own sandboxes, sessions, jobs, snapshots and schedules, and change only environments they created; admins see everything. A person's own credential (`hangar cred add` by a member, `hangar cred owner` by an admin) goes only into their sandboxes and replaces the environment's shared one for its harness. Members mint their own `mcp` tokens (`hangar connect`) and approve OAuth connectors as themselves. Existing tokens belong to `owner`, an admin, so single-owner installs work as before. Records carry `person`, the key for per-person quotas. Credentials stored before people become the owner's own (below). **Rollback note:** a release before people gives every `mcp` token everyone's work, so remove members (`hangar person rm`, which revokes their tokens) before rolling back. [docs/security.md](docs/security.md#people)
- **Team credentials, and the owner's logins stay the owner's** (the owner's decision 5). On its first start hangar makes every credential stored before people the owner's own, once, and records it (`hangar cred migration`), so the owner's Claude and Codex logins never reach a member's sandbox or a job no person owns; control-plane credentials stay the control plane's. Team credentials are a kind of their own (`hangar cred add --team`, `hangar cred owner NAME team`); an admin's credential without `--team` is their own, and a subscription login (a Claude Pro or Max login, a ChatGPT `auth.json`) is refused as a team credential, new or moved. Jobs no person owns (webhooks, schedules without a person, GitHub and Slack senders linked to nobody) use the team's; a person's job uses theirs, else the team's, or as the repo policy says (`credentials: person | team | person_then_team`). A person's Codex ChatGPT logins, leased to one sandbox at a time, form a pool: a job takes a free one, or waits saying which are busy (`HANGAR_LOGIN_WAIT_SECONDS`, 600). **Linked accounts:** `hangar person link alice github alice-gh` (stored as the account's numeric GitHub id; also `slack T…/U…`, `jira`, `email`) makes that account act as alice: her jobs from GitHub, Slack, Jira and GitHub Projects start without approval and use her login, her caps and budget, her lists, and only she continues them there. `people.resolve_external` is the one call intake makes. `hangar doctor` fails on a subscription login stored as the team's, and checks for work no person owns that has no team credential, and frequent senders linked to nobody. Team credentials are API keys, or other credentials the vendor's terms allow: the consumer terms make a login one person's, and Claude Code's forbid routing requests through a Pro or Max login on behalf of others. [docs/team.md](docs/team.md)
- **Scopes on capabilities.** The REST and MCP auth paths record the caller's token and scopes (`identity.current`), and MCP tools can require a scope (`@tool(scope="admin")`). Saving an environment that sets `secrets`, `image`, `base`, `runtime_class` or `credential_mode: direct` needs an admin token; an `mcp` token gets a 403-style refusal. OAuth grants act as the token that approved them.
- **Control-plane credentials never reach a sandbox** (hardening B4). An `mcp` token could map the GitHub webhook secret or the Slack bot token into a sandbox through an environment's `secrets:` and read it back, and then forge trusted webhooks. Credentials now have an exposure: webhook signing keys, GitHub App keys, the Slack secrets and the GitHub tokens hangar's settings name are control-plane only, refused by `secrets:`, attached env vars and files alike. `hangar cred exposure <name> sandbox` shares the control plane's GitHub token with direct-mode sandboxes on purpose. **Upgrade note:** a direct-mode environment that attaches the same GitHub token as `HANGAR_GITHUB_TOKEN_CREDENTIAL` or `HANGAR_GATEWAY_CREDENTIAL` now fails to start, with that command in the message. Run `hangar doctor` after upgrading: its `control-plane credentials` check names every such environment before a job fails on it.
- **Repo policy: one set of defaults for every front door.** `hangar repo set acme/app --verify "pytest -q" --env python` (or `PUT /api/repos/policy`) sets a repo's `verify`, environment, harness and model. GitHub issues, Slack, A2A, inbound webhooks, schedules, MCP and REST all apply it; the job's own fields win, and an environment's new `verify:` field is the fallback. Jobs from GitHub, Slack and A2A used to run with no check at all. [docs/repo-policy.md](docs/repo-policy.md)
- **The check on the base commit.** A repo's or environment's `verify` runs once per base commit before the agent starts, shared by parallel jobs on that base. On a red base the agent is told which failures already exist, and only the failures its change adds count against the gate and the draft decision. The job's events and the PR body say "base was red".
- **Budgets that bound a job.** `job_budget` (`max_cost_usd`, `max_tokens`, `max_turns`) caps all of a job's turns together: follow-ups, verify-fix and auto-fix turns, best-of-N attempts (an equal share each) and the judge. Before, each of these got a fresh per-turn budget. A repo's policy can also set a daily spend cap (`hangar repo set acme/app --max-usd-per-day 60`), and `HANGAR_PERSON_MAX_USD_PER_DAY` one per person across all their tokens; new jobs over either wait for approval, and follow-ups are refused. Days start at midnight in `HANGAR_BUDGET_DAY_TIMEZONE` (UTC unless set). [docs/repo-policy.md](docs/repo-policy.md#budgets)
- **No more stray `HANDOFF.md`.** The `repo-conventions` skill no longer asks agents to write it, and delivery keeps new agent scratch files (`HANDOFF.md`, `RESULT.md`, `NOTES.md` at the root, `*.orig`, `*.rej`) out of PRs unless the task names them.

### Work comes in from Jira and GitHub Projects

- **Jira and GitHub Projects intake.** An issue moved to a configured status (or given a label) in a mapped Jira project, or an issue moved to a configured column on an organization's GitHub Projects board, becomes a job (`HANGAR_JIRA`, `HANGAR_GITHUB_PROJECTS`). Jira comes in through an admin webhook (signed with its secret, `X-Hub-Signature`) or an Automation rule's web request, at `/api/hooks/jira`; project items through the GitHub webhook route. Hangar writes back as the job runs: a comment with a link when the agent starts, the agent's question (the job's person answers it in a comment), the outcome with the PR (a remote link in Jira), and a status transition or column move per stage. Jira Cloud and Data Center. The Jira credentials are control-plane only. A job belongs to the person the Jira account or GitHub user (by user id) is linked to, who is trusted, and only they continue it; an Automation request's body can't say who acted (hangar reads it from the issue's history); the issue's text always reaches the agent fenced as untrusted; an unlinked sender's job (a project-board mover not in `HANGAR_GITHUB_TRUSTED`) waits for a teammate's approval and runs on team credentials. [docs/intake.md](docs/intake.md)

### An approval lands the PR

- **An approval lands the PR, with the human gate kept.** Agent PRs come from a GitHub App (`HANGAR_GITHUB_APP_CREDENTIAL`), whose tokens are minted per repo with `contents` and `pull_requests` write only, so the person who asked can approve them; the gateway's App tokens drop to `contents: write`. With `land: auto_after_approval` in the repo policy, an approval of the PR's head by one of its `approvers` or a code owner, plus green required checks, makes the control plane arm auto-merge for exactly that commit (`expectedHeadOid`), or merge it with `sha` when it is already mergeable. Any push clears the approval and disarms, and no agent turn starts while armed. Jobs record `landing.pr_state` (open, approved, merged, closed), `merged_at` and the time from green checks to merged. A merged or closed PR ends the job's session (final checkpoint, then the sandbox goes), and schedules update their open PR instead of opening another. Each agent PR gets a review packet comment (verification and base-red, cost and budget, harness version and model, files, risk tier from `risk_paths`, session and demo links). `hangar doctor` warns when the branch protection lacks required reviews, stale-approval dismissal or approval of the latest push. A "needs you" inbox: `hangar://inbox`, `hangar inbox`, `GET /api/inbox`, per person, with PRs to review, agents' questions, approvals (agents' secret and egress requests among them) and failed jobs. **Upgrade note:** the webhook needs the `pull_request` event (`hangar doctor --fix`). [docs/landing.md](docs/landing.md)

### Environments that live with the repo

- **`.hangar/environment.yaml`: the repo describes its own environment.** `install` (idempotent, runs on every build), `start` (once per sandbox), `terminals` (long-running processes), `verify` and `extends`, committed next to the code. The file is untrusted. It is parsed strictly (no unknown fields, no YAML aliases, under 64 KiB) and read from the commit, never the working tree. It can't set what an admin decides (image, base, secrets, credentials, MCP servers, runtime class, resources), and a file that tries is refused with that reason. Per field, the job wins, then the file, then the repo's policy, then the environment. Environment specs take the same `install`, `start` and `terminals` fields. `hangar env check` and `POST /api/envbuilds/validate` validate a file without saving anything. [docs/environments.md](docs/environments.md)
- **Versioned builds: agents start with the dependencies installed.** A repo with an `install` gets builds: the environment's image, a clone of the default branch, then `install`, run in an ordinary sandbox under the environment's isolation. The checkout is kept as an image (`ADD`ed, no `RUN`), per provider (Docker and Kubernetes), keyed by the repo, the environment, the provider, the install, the lockfiles' git blob ids and the environment's image. Builds run only in the background: after a clone hangar notices the repo or the environment moved on, and startup's prebuild catches environment changes. A failed build never replaces the active one. Sandboxes fall back to the last good build, or to the environment's image with a warning at the top of the agent's instructions and in the job's events. `get_sandbox` shows `env_build` (version, fallback, stale, reason). Each repo keeps its last 5 builds (`hangar env builds`, `build-show`, `build-repo`); an admin can roll back, which pins until `hangar env unpin` (audited). Build secret ids the repo names reach the install command only, and the checkout is checked for their values before it is kept.
- **The supervisor: `hangar-agent svc`.** One command for the agent to see (`status`, `wait`, `logs`), start, stop and restart the environment's processes, or to add its own. It runs `start`, keeps `terminals` up (restart with backoff, readiness by port or command) and writes each one's output to `~/.hangar/svc/logs/`, where the agent can search it. It's a standard-library python3 script installed in each sandbox like `hangar-agent`, running as the agent's user. The agent's instructions get a "Your environment" section and a `hangar-environment` skill.
- **Services beside the sandbox.** `services: {postgres: {image: postgres:17, port: 5432}}` runs Postgres, Redis and the like as pod sidecars on Kubernetes, and on Docker as containers on an internal network of the sandbox's own. They share the sandbox's runtime and hardening (uid 1000, no capabilities), are reachable at their name, and are torn down with it. Images must match `HANGAR_ENV_SERVICE_IMAGES` (Docker's official images by default).
- **Preview ports.** `ports:` declares what the sandbox's owner may open in a browser: `hangar sb preview` (or `GET /api/sandboxes/{ref}/previews`) gives a two-minute link to `<port>-<sandbox>.<HANGAR_PREVIEW_DOMAIN>`, which signs that browser in to that origin only. Nothing is public. Only declared ports, owner-scoped, checked on every request, and the app never sees hangar's credentials. Off until `HANGAR_PREVIEW_DOMAIN` is set (`localhost` on a laptop).
- **Hangar's own repo has one:** [.hangar/environment.yaml](.hangar/environment.yaml).
- **Agent-led setup: `hangar env setup <repo>`** (after Cursor's autoinstall). A goal agent reads the repo (CI workflows first) and proposes about ten target commands with the expected outcome. A fresh setup agent makes the core ones work: services from the allowlisted images, terminals under `hangar-agent svc`, stand-ins recorded under the file's new `mocks:` field, missing secrets filed with `hangar-agent env request secret` and never invented. Hangar then validates the proposal itself: `envbuilds.validate`, then a clean sandbox of the branch (no build, the proposed services, no agent, person or build credentials) that runs the file's install through the build path, the supervisor and each command. Exit codes decide first; the goal agent judges the output only where needed. A failure goes back to the setup agent with the output, up to `HANGAR_ENV_SETUP_RETRIES` (5) times, and then the job says exactly what is missing. A pass becomes a PR through the landing path, with an `AGENTS.md` section and the validated commands, mocks and missing secrets in the body and the packet. Secrets still missing make it a draft. Also `POST /api/env/setup`, a job label (`hangar.kind: env-setup`), and an issue labelled `hangar-env-setup` on GitHub, Jira or GitHub Projects. `--drift` (and `--every CRON`) re-runs it only when the repo's build broke. Both agents run on the `balanced` model policy, resolved and pinned on each one's session (`HANGAR_ENV_SETUP_MODELS` pins a model or policy per harness), within a job budget split between them. The PR is opened only if the branch is still at the commit hangar validated, and `.hangar/**` is high risk in every packet. [docs/environments.md](docs/environments.md#agent-led-setup)

### Enterprise IT for agents: egress, secrets, cloud credentials

- **Egress allowlists by hostname.** An environment's `egress.mode` is `open` (as before, and the default through `HANGAR_EGRESS_DEFAULT`), `allowlist` or `none`. Proxied sandboxes reach only the git gateway and hangar's egress proxy, with no DNS: a NetworkPolicy and the SandboxTemplate's own policy on GKE, an internal Docker network (`hangar-egress`) on a Linux host. The proxy runs beside the git gateway, never terminates TLS, and checks each connection's host, its SNI or `Host`, and the public address it resolves to. It allows the harness's own API hosts, presets (`packages`: PyPI, npm, crates, the Go proxy, GitHub), the environment's and repo policy's `allow`, and hosts an owner approved after `hangar-agent env request egress`. A repo policy can only tighten the mode. Denials are audited per sandbox and person and show up in the session; allowed traffic is audited per host every minute; `hangar_egress_*` metrics. E2B and Docker Desktop can't enforce it, so proxied environments don't start there. [docs/security.md](docs/security.md#egress-allowlists)
- **Secrets are scanned for before anything leaves.** Before hangar pushes a job's branch it scans every new commit's patch (a token added and deleted later still leaves with the push), the uncommitted and untracked change, and the commit messages. It looks for stored credential values and their encodings, and for GitHub, Slack, AWS, Google, Anthropic, OpenAI, npm, PyPI, GitLab, Stripe, Hugging Face, private-key and hangar token formats. A hit blocks the push. The agent gets a follow-up turn with each file and line (never the value) to remove it and rewrite the commits, up to `HANGAR_SECRET_SCAN_ROUNDS` (2); after that the job fails as `secret_found` with nothing pushed. A 60 MB change scans in about half a second. PR titles and bodies, GitHub and Slack comments, and text artifacts are masked; a binary artifact holding a stored value is withheld. `HANGAR_SECRET_SCAN=block|warn|off`. [docs/security.md](docs/security.md#secret-scanning)
- **Redaction catches encoded secrets** (hardening B4). `broker.redact` also masks stored values reversed, in hex, in base64 at any alignment (line-wrapped too) and percent-encoded, so `printf %s "$X" | rev` no longer prints a stored secret. The docs say plainly what redaction can't stop. [docs/security.md](docs/security.md#redaction)
- **Build secrets** reach only an environment's image build, never the running sandbox. An admin maps them in `build_secrets` on the environment or the repo policy; a repo's file can only name ids. They're passed as BuildKit secret mounts, with values never on a command line or in the build log, and install steps are checked for leftovers. [docs/security.md](docs/security.md#build-secrets)
- **Short-lived cloud credentials instead of stored keys.** An environment's `cloud:` (admin) makes hangar an OIDC issuer for its sandboxes. Each gets an RS256 ID token for one audience, valid `lifetime_minutes` (60), renewed only while the sandbox runs. Its subject is the environment that sets `cloud:` (`hangar:env:<name>`): grant on that, or on `person`, never on `repo`, which whoever starts a sandbox picks. For GCP, an `external_account` configuration lets Workload Identity Federation exchange it (`GOOGLE_APPLICATION_CREDENTIALS`, gcloud too). For AWS, `AWS_ROLE_ARN` and `AWS_WEB_IDENTITY_TOKEN_FILE` drive `AssumeRoleWithWebIdentity`. The keys are in the vault, with discovery at `/.well-known/openid-configuration`, JWKS at `/oidc/jwks.json` (uploadable to GCP, so hangar can stay private) and `POST /api/cloud/rotate` (old keys are unpublished 12 hours later, or at once with `drop_old`). [docs/security.md](docs/security.md#short-lived-cloud-credentials)
- **Egress closed further (Wave 3, egress2).** The proxy reads the whole ClientHello before relaying it and refuses Encrypted ClientHello (`encrypted_client_hello` 0xfe0d per RFC 9849, `ech_outer_extensions`, draft ESNI; GREASE too, so the computer image turns ECH off in Chromium), more or fewer than one server name, SSL 2/3 hellos, repeated extensions, and a second hello after a HelloRetryRequest that fails the same checks. With the git gateway configured, the `pypi`, `npm` and `go` presets read through hangar's **read-only package mirror** (`/pkg/<ecosystem>/` on the gateway: GET and HEAD only, no client credentials, so publish endpoints are unreachable by construction), with a disk cache, or Artifact Registry remote repositories on GKE (`HANGAR_PACKAGE_MIRRORS`); Go is served from the module proxy's cache only, so a module path can't make it fetch from an origin. `packages` no longer opens GitHub, and `crates` no longer opens crates.io (its publish API). Gateway-mode sandboxes read their own repo's REST API, read-only, at `$HANGAR_GITHUB_API` (`curl -n`). One person's sandboxes share `HANGAR_EGRESS_MAX_CONNECTIONS_PER_PERSON` (640) tunnels, and a restart lets open tunnels finish for `HANGAR_EGRESS_DRAIN_SECONDS` (20). The threat model now says which CDNs still allow domain fronting. [docs/security.md](docs/security.md#what-egress-doesnt-stop)
- **The agent's own pushes are scanned (Wave 3, egress2).** The git gateway advertises `no-thin`, holds each push (up to `HANGAR_GATEWAY_SCAN_MAX_MB`, 64), rebuilds the pack's objects and scans its commits, file names and new files with the delivery scan's patterns, in a worker thread, before any of it goes upstream. A hit refuses the push with `file:line` and the kind in git's output, never the value (`secret.found`, `source: gateway`); a hit already in the file the push builds on doesn't count. [docs/security.md](docs/security.md#the-agents-own-pushes)
- **Least privilege: jobs only fetch, hangar pushes; builds hold nothing** (the two Medium gateway-scope findings of the Wave 3 reviews). Every job's sandbox (follow-ups, auto-fix rounds, best-of-N attempts, env setup's agents, the Cloud Doctor's root-cause and fix jobs) gets a **fetch-only** gateway grant: a push is refused at its first request (`hangar: this sandbox may fetch but not push`), so no agent pushes a branch that `push` workflows would run on. After verify, the secret scan and the landing checks, hangar pushes the commit it checked with a grant of its own pinned to that branch and that commit for 10 minutes (`gateway.grant` with `delivery: true`), dropped when the push ends; the gateway refuses anything else with it and scans the pack as before. With the gateway configured, `credential_mode: direct` and `HANGAR_GATEWAY_FOR_JOBS=false` no longer put a git token in a job's sandbox (a git credential in `secrets:` is left out, with a warning); without it, landing still never lands a direct-mode job. Sessions keep a branch-scoped grant, their pushes scanned in the gateway. A repo build's sandbox and env setup's validation, which run the repo's `install`, get the fetch-only grant for their clone, the build secrets an admin mapped (builds only, in `install`'s environment) and egress per policy, and nothing else: no credential (without the gateway not even git's), no `secrets:`, no cloud tokens. [docs/security.md](docs/security.md#jobs-only-fetch-hangar-delivers)
- **Cloud tokens live an hour at most, and keys can rotate on a schedule (Wave 3, egress2).** `lifetime_minutes` is 5 to 60 (retired keys leave the JWKS an hour later), and `HANGAR_OIDC_KEY_ROTATION_DAYS` publishes the next signing key a week before it signs (`cloud.key.next`).

### Restarts, the power schedule and deploys

- **Restarts and the nightly power cycle strand nothing.** One reconciler, on a task of its own (`reconciler.py`), runs at startup and every `HANGAR_RECONCILE_INTERVAL_SECONDS` (30). A sandbox a restart left `pending`, `starting` or `stopping` is finished: a create is torn down and its exclusive lease freed at once (a Codex login was blocked for the sandbox's 4-hour TTL), a destroy is completed, and a create that never stored its provider ref is found by its label. On GKE the pod UID is recorded, so a pod that node repair or a scale-down recreated blank under the same claim counts as gone; its session resumes from its checkpoint, and envd's address is cached per pod. A destroy's provider steps run on a task of their own, so a cancelled caller no longer leaves a sandbox `stopping` forever. Each sandbox it acts on gets `failed_stage`, `cause` (`orphaned_by_restart`, `pod_replaced`, `gone`) and the create's `stages` in `info`.
- **Interrupted jobs resume instead of failing.** A job a restart caught mid-turn, whose session has a checkpoint, gets a follow-up turn that resumes from it; one caught provisioning starts over. Each does so at most `HANGAR_JOB_RESTART_RESUMES` (2) times, and they re-enter the queue `HANGAR_JOB_RESTART_STAGGER_SECONDS` (20) apart.
- **GitHub deliveries missed while hangar was down are redelivered.** At startup hangar asks GitHub to redeliver each failed delivery of the repos' webhooks since the last start, and a delivery is marked handled only after its handler returns, so one a dying pod half handled runs again.
- **`power.sh down` drains first.** `POST /api/admin/drain` holds queued jobs; the script waits for creates, destroys and suspends in flight, checkpoints the turns still running, and only then powers the sandbox pools down (hangar itself stays up: below).
- **Heartbeats for background loops:** `hangar_loop_last_tick_timestamp{loop}` and `hangar_loop_failures_total{loop}` for the reaper, reconciler, sessions, schedules and backups.
- **The control plane stays up overnight; only the sandbox pools power down.** `power.sh down` scales the `sandboxes-*` pools (gVisor, Kata, microVM) to 0 and leaves hangar and the system pool up: GitHub, Slack, Jira and GitHub Projects events are queued, jobs wait with `waiting: sandboxes power on at 10:00 EDT`, and creates (REST, MCP, E2B, sessions) answer at once with that time (REST `503` with `Retry-After`) instead of waiting for a node. A job turn the power-down cuts off resumes from its checkpoint at power-up. The microVM pool comes back at its fixed size instead of autoscaling 0–4. `hangar power` shows the state; `hangar power up` (`POST /api/admin/power/up`) runs the power-up job early. [docs/gke.md](docs/gke.md#6-sandbox-nodes-off-at-night-optional)
- **A warm start at 09:50.** The gVisor pool comes back at a warm floor (`sandbox_warm_nodes`, 1), the `hangar-prepull` DaemonSet pulls every image and pack `hangar images plan` lists onto it, and then queued jobs start and each environment's warm pool is sized from last week's creates in the 10:00 hour (`HANGAR_POWER_WARM_POOLS`, `HANGAR_POWER_WARM_MAX`). The acceptance script's `warmstart` check times a warm and a cold create; `power` checks the refusal while the pools are off.
- **Gated deploys: `.github/workflows/deploy.yml`.** By hand or on a `v*` tag: images and the control-plane image, the owner's approval (`production` environment), `kubectl set image`, the rollout, `gke.sh` with no kubectl in its checks, the tool-list diff and server version in the run summary, and a rollback to the image it replaced on any failure, a cancel included (a doctor check that was already failing is reported, not rolled back for). The deploy's secrets are `production` environment secrets, released only on approval, and its identity can only patch the `hangar` Deployment. It refuses while the sandbox pools are off unless forced, and records each deploy in hangar. [docs/upgrading.md](docs/upgrading.md#deploying-with-deployyml)
- **One script sets up deploying from CI/CD: `deploy/gke/setup-cicd.sh`.** Run once from the owner's machine (`--dry-run` prints every change first; safe to re-run), it creates the Workload Identity Federation pool and provider (this repository only, by name and numeric id, and only push or manual runs of `main` or a `v*` tag), one service account per workflow role (`hangar-ci`: Artifact Registry writer on the `hangar` repository; `hangar-deploy`: `clusterViewer` and a namespaced Role on `deployments/hangar`, impersonable only from the `production` environment, under both GitHub's name-based and immutable subject; the canary gets none), the `production` environment with the owner as required reviewer, a tag ruleset so only repository admins create `v*` tags, and the repository and environment secrets the workflows read, with an admin token minted into `HANGAR_DEPLOY_TOKEN` on stdin, never printed. It copies the vault key into Secret Manager, creates the package mirrors' remote repositories, prints the quota requests, the terraform apply and a checklist of what needs a person, then checks it all read-only and prints the command for the first deploy. It narrows an earlier setup: repository copies of deploy secrets, any project role beyond `clusterViewer` on either account (`roles/container.developer` included), other federated identities bound to them, and a provider any ref could use; the check fails if another provider shares the pool. **Fix:** the deploy Role lacked `list`, which `kubectl rollout status` needs, so the first deploy would have failed as forbidden. `images.yml` skips, and `deploy.yml` refuses, on refs Google Cloud doesn't trust. [docs/cicd.md](docs/cicd.md)
- **Infra states: hold, off, and deploys only while up.** `power.sh hold --days N|--until DATE` pauses the power schedule (the scheduled jobs read the hold from the cluster's labels first and exit with a log line; it ends by itself and the schedule resumes, nothing powers up early); `power.sh release` ends it, and `hangar power hold`/`release` (admins, CLI and REST, no MCP tool) do the same through hangar, copied to the cluster by the next scheduled run. `power.sh off` takes everything to zero compute (the drain and suspends of `down`, the sandbox pools, hangar, then the system pool once hangar's pod is gone) and holds it off 7 days; nothing is deleted, the `hangar-data` disk included. `power.sh up` from off brings the system pool, then hangar, then the sandbox pools back, ends the hold, and starts `deploy.yml` for main when main is ahead of what hangar runs (it waits for approval; the scheduled power-up holds no GitHub credential and reports a deploy pending in `hangar power` and doctor instead). `deploy.yml` runs on merges to main: a read-only `state` job (`hangar-state@`, `container.clusters.get` only; `setup-cicd.sh` creates it) skips green while the infra is off, held or down, and coalesces a burst of merges. `hangar status`, `hangar power` and doctor show the hold. [docs/cicd.md](docs/cicd.md#infra-states), [docs/gke.md](docs/gke.md#infra-states)
- **Operator view.** `hangar doctor`, `GET /api/overview` and MCP `fleet_overview` show the power state, the last deploy and its acceptance result, and whether the reaper, reconciler, session and schedule loops pass on time. No new MCP tools.
- **The acceptance suite proves the team release on the cluster, safely on a production install.** `scripts/acceptance/gke.sh` gains `computer` (Chromium under gVisor, a whole PNG of the display's size, 3 s of video, a screen ticket whose view-only viewer can't move the pointer), `egress` (allowed host through the proxy, 403 otherwise, no direct route, no DNS, and with `--with-model` an agent's `env request egress` pending for its owner), `services` (Postgres by name), `envbuild` (a fixture repo builds; a broken install keeps the good build active; `svc`'s dev server; a preview link that works once), `secrets` (a job holding a synthetic token isn't pushed, its events name file and line), `landing` (the PR from the GitHub App; an approval arms auto-merge, a push disarms it), `intake` (a signed synthetic Jira delivery makes a job for the linked person), `scale-smoke` (20 sessions over MCP across 3 test people: caps, isolation, p95 create, no leaks; with `--with-model`, the fair job queue), `power --power-cycle` (pools down and up, timed), `prepull` (the first create after power-up pulls no image), `status` (`hangar status` answers with its sections, and says whether jobs' `frontier` default is capped) and `clouddoctor` (a Cloud Doctor dry run). Dedicated test environments (`accept-*`, kept so their images build once), test repos and test people; everything else it makes is removed at the end, after a failure too, PRs, repo policy and the fixture's file included. Each check's timings go to a JSON report, with what `--with-model`'s turns spent (each capped by `--max-usd`); `deploy.yml` runs the core checks (`--only core --gate core`), which alone decide a rollback, then the team checks in a step that can't fail the deploy. A `credential health` failure (a person's login expiring during the deploy window) is reported by the `doctor` check, never a rollback (`deploy_gate: false`). The power cycle refuses while anyone else has a live session, an active job or a sandbox; cleanup puts back only the policy fields and fixture files that still hold what the run set. No kubectl. The runbook for the first live run: [docs/acceptance.md](docs/acceptance.md).

### The Cloud Doctor, the operator console, flight records and credential health ([docs/doctor.md](docs/doctor.md), [docs/observability.md](docs/observability.md))

- **`hangar status`, `GET /api/status` and the resource `hangar://status`**, for admins: the power state and last deploy, each background loop's last pass, harness versions (locked, and what each provider's pack installed), builds running, the day's failures by cause (transient or not), egress denies by host, requests waiting for an answer, SLOs (create p50/p95 warm, cold and on a build path; turn start; resume hot and cold, against the observability review's targets), credential health, the nightly pass, and the last warnings hangar logged (its own loggers only, never `uvicorn.access`, each line through `broker.redact`). No new MCP tools: `fleet_overview` gains `failures_24h` and `credential_health`, `list_credentials` gains `health`, `last_ok` and `expires_at`, and `get_job` gains `flight_record`.
- **Flight records** for every job that fails or times out, every session turn outside a job that does, and every job or turn that ran slow against its environment's norm (3× the median of its last 50 clean runs, and 2 minutes over it). Each holds the create's stage history, the end of the run log (256 KB, masked like secret scanning masks, gzipped and sealed with the vault key like a checkpoint part, read and written only once the session is idle), what `env doctor` reports, egress denies, unanswered requests, versions, cost, and a cause decided without a model (`missing_tool`, `egress`, `install`, `model_api`, `pod_replaced`, …) with whether it looks transient. Kept 14 days. `hangar admin records ls|show [--log]`, `GET /api/records`, `GET /api/jobs/{id}/record`, `hangar://jobs/<id>/record`.
- **Credential health, without a model call.** `claude setup-token` tokens by age (they last a year), Codex ChatGPT logins with `codex login status` in the login's sandbox when captured (and by what it checks, elsewhere), Google service-account keys with gcloud in a config of their own (`activate-service-account`, `print-access-token`, the key's `validBeforeTime`). Results go on the credential (`health`, `last_ok`, `expires_at`); a credential that stops working or expires within 14 days shows in `hangar doctor`, `hangar status` and the inbox of whoever renews it (the person for their own, admins for the team's), and a pool with no working login fails the doctor. `hangar cred check [NAME…]`.
- **The nightly pass** at `HANGAR_DOCTOR_SCHEDULE` (`30 0 * * *`, in the power schedule's time zone): credential checks, then the Cloud Doctor. The `ops` loop (SLO samples, record pruning, the nightly pass) has a heartbeat like the others.
- **The Cloud Doctor** ([docs/doctor.md](docs/doctor.md)). Every night (or `hangar admin doctor run`) it reads the flight records since its last run and groups them by kind. Transient causes are counted, and reported only when one keeps coming back. A real one seen in 2 separate runs: a host agents keep being denied, or a secret they keep asking for, becomes a request in the admins' inbox with the evidence (never granted by the doctor); the rest gets one root-cause job per repo, in the repo's own environment, on team credentials, on the `balanced` policy for every harness (Opus on Claude Code), resolved and pinned on the job's session, unless `HANGAR_DOCTOR_MODEL` says otherwise (`frontier`, or `best` for that on a Claude Code team key that may lack Fable access), the evidence handed over as an untrusted file, and a structured answer. Only a high-confidence fix to a skill, `.hangar/environment.yaml` or an environment spec becomes a PR, through the landing path, carrying the runs, jobs and records it rests on; before it is pushed, hangar refuses a change outside those files or to any credential, secret, egress or isolation field. Everything else is a report in the admins' inbox. Its jobs carry job budgets, and a run's jobs together stay under `HANGAR_DOCTOR_MAX_USD` ($10). Findings close themselves when the PR merges, the request is approved, or the failure stops. `hangar admin doctor ls|show|dismiss`, `/api/admin/doctor`, and a `doctor` section in `hangar status`. `hangar admin doctor run --dry-run` (`GET /api/admin/doctor/plan`) says what a run would do, changing nothing.

### MCP

- **No MCP tool dies with its client, and every one answers within the budget.** `create_sandbox`, `create_sandboxes`, `fork_sandbox` and `build_environment` answer within `HANGAR_MCP_TOOL_WAIT_SECONDS` (150 s). Past that they return the sandbox or build as it stands (`starting`, with a `stage` saying what it waits on) and keep going in the background. Before, an MCP client that gave up on the call (claude.ai stops after about 230 s) cancelled the create, and the sandbox ended in `error`. Destroy, pause, resume, extend, snapshot, `fork_session` and `run_agent` now run on their own task like create, and answer with the work as it stands after `HANGAR_MCP_TOOL_WAIT_SECONDS`. `wait_for_turn` (300 s by default before), `exec`'s `timeout`, `process` `attach` and `terminal_send` waits are capped at it. A test calls every tool against a provider that never answers and fails on any that outlives the budget, so a new tool can't reintroduce the bug. `create_sandboxes`, which the first half of this broke, works again.
- **`build_environment` called again returns the running build** instead of queueing a second job with an empty log (and, with `force`, a second Cloud Build).
- **Stale tool lists are called out.** `serverInfo.version` is `<package>+tools.<hash of the tool list>` instead of `0.1.0`. The claude.ai apps never refetch the tool list, so a call from a client working from an older one gets a line asking to remove and re-add the connector (at most hourly), and an unknown tool's error says the same.
- **`hangar sb exec box -- cmd 'a b'` keeps its quoting** (`shlex.join`); a single argument is still a shell line.
- **An `mcp` acceptance check:** `create_sandbox` over MCP on a multi-harness environment within claude.ai's 230 s, a create whose client drops still comes up, then `exec`; no kubectl needed.

### Images and packs

- **Images and packs are built before anyone waits, and harness versions are pinned.** `hangar images plan` lists every environment image and harness pack tag the code needs on a provider and which the registry lacks (one HTTP request per tag, no `gcloud` process); `hangar images build` builds and pushes them. CI runs it on every push to main (`.github/workflows/images.yml`, Workload Identity Federation; it skips cleanly until the secrets exist) and `deploy/gke/up.sh` before rollout. `src/hangar/harnesses.lock.yaml` pins every harness (Claude Code 2.1.296 and Antigravity 1.3.3 by vendor checksum, no longer "latest"). A pack build fails unless the CLI reports the locked version, and records what it reported: `list_environments` (`harness_versions`), `hangar pack list` and every turn (`harness_version`) show it. Packs are mounted by digest (`repo@sha256:...`), and `hangar pack publish` no longer overwrites an existing tag without `--force`. In the cluster, image checks ask the registry over HTTP instead of spawning `gcloud`. **Every pack tag changes once with this release**: let CI (or `up.sh`) build them before rollout. [docs/gke.md §3](docs/gke.md#3-environment-images).
- **Harness packs hold the vendor's files, not hangar's launch glue.** Codex's pack has no wrapper script any more: `bin/codex` links to the vendor binary, and hangar adds the bundled `rg` to `PATH` when it sets up the sandbox. A change to how hangar starts a harness no longer changes a pack's digest, which is how #69 forced a Codex rebuild. pi's and Gemini's launchers name their prefix instead of finding it through `dirname` and `readlink` on the agent's `PATH` (harness review B5). This ships in the same release as the pinned harnesses above, so pack digests change once.
- **The harness contract runs in CI, and a nightly canary moves the lock.** The real-CLI tests (driver, harden, verify gate, prompt cache, and new protocol tests) used to skip in CI. They now run against the locked CLIs on every PR that touches harness, driver or isolation code and on main (`harness-contract.yml`; CLIs installed by the packs' own recipes, without root, and cached; a skipped test fails the job). The recorded protocols (Codex's app-server schema as the driver uses it, Claude Code's stream-json messages) live in `tests/fixtures/protocol/` and must match the locked CLIs. Each night `harness-canary.yml` resolves every harness's newest stable release from the vendors' own sources, downloads and checks the published checksums, runs the contract tests against those versions and diffs the protocols. All green: one lock-bump PR whose body is the review packet. Anything red: one `harness-canary` issue with the failures. The bump lands on one approval of its head by an approver (`harness-canary-land.yml`, #96's rule, diff limited to the lock and the records), never without one. Sessions are pinned to the CLI version locked when they were created: a follow-up on a sandbox with a newer CLI hands off instead of resuming. [docs/harnesses.md](docs/harnesses.md)
- **`model: balanced` and `frontier`: the latest strong models per provider, resolved and pinned.** Environments, repo policies, jobs and sessions take a policy (`frontier`, `balanced`, `frontier@openai`) as well as an id. It is resolved to a concrete id when a sandbox or session is created, from Anthropic's `/v1/models`, OpenAI's and Google's model lists, and OpenRouter's for pi. Lists are cached (`HANGAR_MODEL_LIST_TTL_MINUTES`) and refreshed in the background; without one, hangar uses the last resolved id, else a built-in one, and says so. The id is pinned on the session (`model`, `model_policy`) and sandbox (`get_sandbox` → `model`), and shown per harness in `list_environments` (`models`). **`balanced` is the default everywhere** (the owner's decision): jobs, `envs/bare.yaml`, env setup (`hangar env setup`) and the Cloud Doctor (`HANGAR_DOCTOR_MODEL` unset). On Claude Code it is Opus (`claude-opus-5-5` today, by the `line` rule); `frontier` (Fable 5.1, about 2.5 times the price) stays available per environment, repo policy or job. **Hangar sets no spend cap**: until `HANGAR_JOB_BUDGET_MAX_COST_USD` or `HANGAR_PERSON_MAX_USD_PER_DAY` is set, `hangar doctor` warns (`model spend`: jobs have no budget) and `hangar status` says so on its `models` line, whatever the default. **`envs/bare.yaml` now says `model: balanced`** for every harness, instead of the alias `opus`, flash tiers for pi and Antigravity, and Codex on its account default. API keys for the lists: `HANGAR_MODEL_LIST_CREDENTIALS`. [docs/harnesses.md](docs/harnesses.md#models-the-latest-strong-model-per-provider)
- **A create waits only on its own harness's pack.** Packs for the environment's other harnesses are mounted when they're already built. A stale one, after an upgrade changed that harness, is rebuilt in the background instead of holding up the sandbox. This is why the first `python` sandbox after the #69 upgrade took minutes: it rebuilt the Codex pack for a Claude Code sandbox. The image build a create triggers (first use, or an environment change) also builds just that harness's pack, side by side with the image. Scheduled warm-pool syncs never wait on a build. At startup, packs whose harness changed in the upgrade are rebuilt in the background. A create that does wait on its own pack says so in `stage`, with the time so far.

### Review fixes: trust, dedupe and restarts (Wave 3)

- **An auto-fix review round needs a reviewer the job's person or the repo trusts** (#91's open finding). A round runs with the job's person's login, so on a person's job only their linked account, an admin's, the repo policy's `approvers` or a code owner of every touched path starts one; a team job also takes anyone the GitHub front door trusts. Bots and hangar's own App never do. Every reviewer's text is now an untrusted attachment, each comment fenced and labelled with its author; the instruction is hangar's. Rule 6 in [docs/team.md](docs/team.md#who-is-trusted). **Upgrade note:** a collaborator who isn't linked, an approver or a code owner no longer starts rounds on members' jobs.
- **Slack events are marked handled after they are** (commit after handle, as #84 did for GitHub): a Slack retry of an event a dying process acknowledged but never handled now runs.
- **A restart or a lost sandbox during the base check provisions again and checks the base again** (#82), through #84's restart path, instead of resuming without a baseline (so the base's own failures failed the job) or failing.
- **A Jira delivery over 1 MB is audited (`jira.too_large`) and answered on its issue** (#92): when authentic and its issue waits for an agent, hangar comments once a day that the description is too large. It was dropped without a word.
- **Missed GitHub Projects deliveries are redelivered at startup** (#92): the startup pass also covers each `HANGAR_GITHUB_PROJECTS` organization's webhook (`projects_v2_item`), with the organization's Webhooks read and write permission.
- **Best-of-N attempts the power-down cuts off resume at power-up** (#95), each from its own checkpoint, instead of each failing (`sandbox_gone`).
- **Auto-merge is armed only when the base branch dismisses stale approvals** (#96 finding 7). Otherwise, or when hangar can't read the protection, it doesn't arm and `hangar doctor` fails with the fix; `hangar repo set owner/repo --no-require-stale-dismissal` opts a repo out.

### The heavy tier: Docker inside a VM, and bigger sandboxes (Wave 4, #117; [docs/environments.md](docs/environments.md#the-heavy-tier))

- **Docker in the sandbox, on a VM of its own, deny by default.** `heavy: true` (or `tier: heavy`) on an environment (an admin's), `hangar repo set acme/app --heavy on`, or `heavy: true` in a repo's `.hangar/environment.yaml` where an admin allowed it (`--heavy allow`; the owner's decision: a repo's own file only *requests* Docker, and unset is `deny`) runs the sandbox on the heavy tier: a Kata microVM on GKE's new `sandboxes-heavy` pool, or an E2B/CubeSandbox microVM, per `HANGAR_TIERS["heavy"]` (off until set; it never falls back past its providers). The image gets dockerd, containerd, runc and the docker CLI with Compose and Buildx (`HANGAR_HEAVY_DOCKER_IMAGE`, `docker:29.8.2-dind`); `hangar-docker` starts dockerd as root inside the VM at claim (a loop-mounted ext4 disk where `/var/lib/docker` is virtio-fs, cgroup nesting, the pod's MTU), so `docker build`, `docker compose` and Testcontainers work and their containers stay in the VM, under the pod's network policy. gVisor stays the default; why Kata and not Docker-in-gVisor is in the docs. On a cluster with GKE's Agent Sandbox add-on, whose policy refuses privileged Kata pods, use the open-source controller or microVMs. [docs/environments.md](docs/environments.md#the-heavy-tier)
- **Compose stacks under the supervisor.** `services: {deps: {compose: docker-compose.yml}}` (or `deps: docker-compose.yml`), and `hangar-agent svc add NAME --compose FILE`: the supervisor runs `docker compose up`, restarts it, keeps its log, and `start` waits until every service is running and healthy (or a `port`/`ready` says so).
- **Resource profiles.** `standard` (2 vCPU / 4 GiB), `large` (8 / 32 / 100 GiB) and `xlarge` (16 / 64 / 200), set on an environment (`profile:`), a repo's policy (`--profile`, and `--max-profile` for what a job or the repo's file may ask for) or a job (`hangar job submit --profile large`, label `hangar.profile`). Large and xlarge run on the heavy pool. One person holds at most 3 large-or-larger and 1 xlarge sandboxes (`HANGAR_HEAVY_PERSON_MAX`), and work no person owns (unlinked senders' jobs, webhooks) shares one team bucket with the same caps; repo builds aren't counted. Heavy warm pools stay off unless `HANGAR_HEAVY_WARM_POOLS`. Sizing and cost: [docs/team-scale.md](docs/team-scale.md#heavy-tier).
- **Docker images through egress policy.** Allowlist sandboxes' dockerd uses the egress proxy (a new `docker` preset opens Docker Hub). `HANGAR_HEAVY_MIRROR` puts hangar's read-only Docker Hub pull-through on the gateway, upstream Docker Hub or an Artifact Registry remote repository for it (terraform `enable_dockerhub_mirror`, with Docker Hub credentials of your own), read with hangar's Google identity, the sandbox's credential in the mirror path, use in the egress audit. `HANGAR_HEAVY_REGISTRY_MIRRORS` adds others (`https://mirror.gcr.io`).
- **Agents know their tier.** `hangar-agent env doctor` starts with the tier, profile, runtime and whether Docker answers; heavy sandboxes get a Docker section in their instructions and a `hangar-docker` skill. A repo whose file asks for Docker it isn't allowed runs on the default tier, and the agent's instructions, the sandbox's warnings and a `WARN` on the doctor's `tier` line say Docker isn't enabled for the repo and give the admin's command. `scripts/acceptance/gke.sh --only heavy` checks a Compose Postgres and a Testcontainers test; CI runs it on Docker (privileged, `HANGAR_HEAVY_DOCKER_PRIVILEGED`, for CI only).

### Warm caches (Wave 4, #115; [docs/caches.md](docs/caches.md))

- **Dependencies and compile output across sandboxes.** Each repo keeps dependency caches (npm, pnpm, yarn, `node_modules`, uv, pip, `.venv`, Cargo, `target`, Go modules and build cache, Maven, Gradle) keyed by the toolchain and the lockfiles' git blob ids. A lookup falls back to the newest entry for the same toolchain, as `restore-keys` do. They are restored after the clone in the background (`hangar-cache`): the sandbox is ready at once, and the agent is told the caches are warming. Hangar also serves remote compile caches on the gateway's port in the tools' own protocols: sccache (WebDAV), Bazel's HTTP cache (a `~/.bazelrc` block) and the Turborepo remote cache API. Each sandbox authenticates with its git grant, gets the variables it needs, and the repo is left alone. Only a repo's own builds write its shared caches (one per environment); sessions and jobs read them and write a private layer of their own session and branch that nothing else reads; no repo reads another's. Objects are content-addressed chunks sealed with the vault key and checked on every read, in the session bucket's `caches/` prefix, with LRU caps per repo and in total, sizes in `hangar status`, and `hangar admin caches purge`. A fixture project's `npm ci` (162 packages): 4–5 s cold, dependencies back in about 1 s warm. [docs/caches.md](docs/caches.md), [docs/security.md](docs/security.md#build-caches)

### Test results from every check (Wave 4, #116; [docs/jobs.md](docs/jobs.md#8-test-results))

- **Structured results, not an exit code and a tail.** Every check hangar runs (the base check, the check after each turn, best-of-N attempts, agent-led setup's validation, the in-turn gate, the deploy acceptance checks) leaves a test run: counts, failures with their messages, every case by test id, coverage, and the commit and tree it ran on. Hangar sets the reporter variables pytest, gotestsum and jest-junit read and collects JUnit from them, surefire, failsafe, Gradle, nextest and vitest, plus Cobertura and LCOV coverage; `verify_reports` (in `.hangar/environment.yaml` or the repo policy) names any other path. `HANGAR_TEST_REPORTS=collect|off`. One parser for all of it (`testreports.py`, which the harness canary now uses too), with defusedxml's rules and size caps, since reports are written by the repo's code.
- **Red bases, exactly.** When both the base check and the check after the turn left complete reports, new failures are the failing test ids minus the base's, instead of ids read from the output's text (which stays the fallback). A check that printed nothing readable no longer makes the PR a draft with `base_red`.
- **Flaky tests.** A test that passed and failed on the same tree, or that the runner passed on a retry, goes on its repo's flaky list. `rerun_flaky` in the repo policy runs a check once more when it failed only on listed tests. The review packet marks them, `hangar status` lists the repos with the most, and the Cloud Doctor counts a failed check with only flaky failures as transient.
- **Where it shows.** `result.tests` on jobs and attempts, a `progress` event in the job's and session's events, the review packet (counts, new failures, flaky tests, coverage change against the base), `TEST-RESULTS.json` in the job's directory for the agent (the prompt points at it), `GET /api/jobs/{id}/tests` and `/api/sessions/{ref}/tests` (`?format=otel`), `hangar://jobs/<id>/tests`. In traces, each run is a `test.run` event and a `test.case` event per failing or flaky test (the kinds `hangar.trace/v1` reserves), with OpenTelemetry's test semantic conventions alongside. No new MCP tools.

### Interfaces for the sister tool (Wave 4, #114; [spec 0014](docs/specs/0014-sister-tool-interfaces.md))

Hangar stays the runtime; a sister tool in a separate repository inspects harnesses, draws trace timelines and writes and evaluates behavior specs. It reads three thin, versioned interfaces, all owner-scoped and redacted:

- **The effective harness manifest** (`hangar.manifest/v1`, [schema](docs/api/manifest.schema.json)). The exact configuration a turn ran with: the harness and its locked version, the resolved model, the global instructions, skills and the repo's `AGENTS.md`/`CLAUDE.md` by reference and digest, MCP servers (names, transports, endpoints; never credentials), hooks, approvals and permission mode, egress, the environment and its build, resources, budget and policy. Captured as each turn starts (one command reads what the sandbox actually has), stored with the turn (`SessionTurn.manifest` is its digest), with a `config_digest` over the harness configuration alone. `GET /api/sessions/{name}/manifest?turn=N`, `/api/jobs/{id}/manifest`, `/api/environments/{name}/manifest`, `hangar://sessions/{name}/manifest`, `hangar session|job|env manifest`.
- **Trace export** (`hangar.trace/v1`, [docs/api/traces.md](docs/api/traces.md)). A run, a session or a job as OTLP/JSON on the OpenTelemetry GenAI semantic conventions (pinned: semantic-conventions-genai `gen-ai-dev/1.42.0-dev` on core 1.44.0; development status) plus `hangar.*`, with a stable taxonomy behavior specs match on: `turn`, `tool.call` with normalized tool kinds (`shell`, `edit`, `read`, `search`, `web`, `mcp`...), `subagent`, `approval`, and events for steers, verify, file changes, commits, pushes, PRs and CI. `GET /api/sessions/{name}/trace`, `/api/jobs/{id}/trace`, `hangar trace export`. `HANGAR_TRACE_LIVE_TOOLS=true` also sends each turn's tool spans to the configured collector.
- **Experiment jobs** (`hangar.experiment/v1`, [schema](docs/api/experiment.schema.json)). `hangar experiment run spec.yaml` / `POST /api/experiments`: tasks (prompts with repo refs, or issues) × variants (an environment plus an overlay: harness@version, model or policy, approvals, skills, instructions) × trials, as ordinary jobs under the experiment's budgets and fair share, pinned (harness lock, model id, base commit) and isolated (only the trial's harness pack is mounted, never a warm sandbox; exactly its variant's skills and instructions; egress fixed per experiment). Per trial: the manifest, the trace export, verification, and an optional external grader's output, run in a clean sandbox on the trial's patch. An index of trials, not an analysis: effect sizes and reports are the sister tool's. **Upgrade note:** new data directories `manifests/` and `experiments/` under the data dir; nothing to migrate.

### Sandboxes and providers
