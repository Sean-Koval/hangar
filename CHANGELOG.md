# Changelog

## Unreleased

The team release: Wave 1 (#75–#90) and Wave 2 (#91–#100), one release. One hangar for a team of six at ~60 sessions, with people, team credentials and per-person caps and budgets; work from GitHub, Slack, Jira and GitHub Projects; an approval lands the PR; environments that live with the repo, with services and a computer for every agent; egress allowlists, secret scanning and short-lived cloud credentials; restarts and the nightly power cycle strand nothing, and deploys are gated. **Upgrading a running hangar:** follow [docs/upgrading.md](docs/upgrading.md#upgrading-to-the-team-release-75100), one ordered procedure, in order.

### A team on one hangar

- **One control plane for a team of six at ~60 sessions.** Sandbox, job and session lookups use expression indexes instead of parsing every record ever made (a team load test: `get_session` p50 3.4 s → 42 ms, event-loop lag p95 5.2 s → 70 ms). Stopped and failed sandbox records idle for 7 days move to an archive table, still found by id, never while a snapshot or a credential lease points at them. Caps per person on live sessions (15), sandboxes (20) and running jobs, counted by the person each record belongs to; a fair job queue serves whoever has the fewest jobs running. `HANGAR_MAX_SANDBOXES` goes to 120 and job slots to auto (8 on GKE; 24 by hand once budgets are set). Workspace archives in flight share a 1 GiB memory budget, so a fork can't exhaust the control plane. On GKE: `n2d-standard-16` sandbox nodes (AMD keeps SMT on under gVisor), up to 10; sandbox pods request half their CPU; `power.sh up` keeps an autoscaling range set while the cluster was down. [docs/team-scale.md](docs/team-scale.md)
- **People: one hangar for a team.** Every token belongs to a person, an admin or a member (`hangar person add|ls|role|token|rm`, `/api/people`). Members see and act only on their own sandboxes, sessions, jobs, snapshots and schedules, and change only environments they created; admins see everything. A person's own credential (`hangar cred add` by a member, `hangar cred owner` by an admin) goes only into their sandboxes and replaces the environment's shared one for its harness. Members mint their own `mcp` tokens (`hangar connect`) and approve OAuth connectors as themselves. Existing tokens belong to `owner`, an admin, so single-owner installs work as before. Records carry `person`, the key for per-person quotas. Credentials stored before people become the owner's own (below). **Rollback note:** a release before people gives every `mcp` token everyone's work, so remove members (`hangar person rm`, which revokes their tokens) before rolling back. [docs/security.md](docs/security.md#people)
- **Team credentials, and the owner's logins stay the owner's** (the owner's decision 5). On its first start hangar makes every credential stored before people the owner's own, once, and records it (`hangar cred migration`), so the owner's Claude and Codex logins never reach a member's sandbox or a job no person owns; control-plane credentials stay the control plane's. Team credentials are a kind of their own (`hangar cred add --team`, `hangar cred owner NAME team`); an admin's credential without `--team` is their own, and a subscription login (a Claude Pro or Max login, a ChatGPT `auth.json`) is refused as a team credential, new or moved. Jobs no person owns (webhooks, schedules without a person, GitHub and Slack senders linked to nobody) use the team's; a person's job uses theirs, else the team's, or as the repo policy says (`credentials: person | team | person_then_team`). A person's Codex ChatGPT logins, leased to one sandbox at a time, form a pool: a job takes a free one, or waits saying which are busy (`HANGAR_LOGIN_WAIT_SECONDS`, 600). **Linked accounts:** `hangar person link alice github alice-gh` (stored as the account's numeric GitHub id; also `slack T…/U…`, `jira`, `email`) makes that account act as alice: her jobs from GitHub, Slack, Jira and GitHub Projects start without approval and use her login, her caps and budget, her lists, and only she continues them there. `people.resolve_external` is the one call intake makes. `hangar doctor` fails on a subscription login stored as the team's, and checks for work no person owns that has no team credential, and frequent senders linked to nobody. Team credentials are API keys, or other credentials the vendor's terms allow: the consumer terms make a login one person's, and Claude Code's forbid routing requests through a Pro or Max login on behalf of others. [docs/team.md](docs/team.md)
- **Scopes on capabilities.** The REST and MCP auth paths record the caller's token and scopes (`identity.current`), and MCP tools can require a scope (`@tool(scope="admin")`). Saving an environment that sets `secrets`, `image`, `base`, `runtime_class` or `credential_mode: direct` needs an admin token; an `mcp` token gets a 403-style refusal. OAuth grants act as the token that approved them.
- **Control-plane credentials never reach a sandbox** (hardening B4). An `mcp` token could map the GitHub webhook secret or the Slack bot token into a sandbox through an environment's `secrets:` and read it back, and then forge trusted webhooks. Credentials now have an exposure: webhook signing keys, GitHub App keys, the Slack secrets and the GitHub tokens hangar's settings name are control-plane only, refused by `secrets:`, attached env vars and files alike. `hangar cred exposure <name> sandbox` shares the control plane's GitHub token with direct-mode sandboxes on purpose. **Upgrade note:** a direct-mode environment that attaches the same GitHub token as `HANGAR_GITHUB_TOKEN_CREDENTIAL` or `HANGAR_GATEWAY_CREDENTIAL` now fails to start, with that command in the message. Run `hangar doctor` after upgrading: its `control-plane credentials` check names every such environment before a job fails on it.
- **Repo policy: one set of defaults for every front door.** `hangar repo set acme/app --verify "pytest -q" --env python` (or `PUT /api/repos/policy`) sets a repo's `verify`, environment, harness and model. GitHub issues, Slack, A2A, inbound webhooks, schedules, MCP and REST all apply it; the job's own fields win, and an environment's new `verify:` field is the fallback. Jobs from GitHub, Slack and A2A used to run with no check at all. [docs/repo-policy.md](docs/repo-policy.md)
- **The check on the base commit.** A repo's or environment's `verify` runs once per base commit before the agent starts, shared by parallel jobs on that base. On a red base the agent is told which failures already exist, and only the failures its change adds count against the gate and the draft decision. The job's events and the PR body say "base was red".
- **Budgets that bound a job.** `job_budget` (`max_cost_usd`, `max_tokens`, `max_turns`) caps all of a job's turns together: follow-ups, verify-fix and auto-fix turns, best-of-N attempts (an equal share each) and the judge. Before, each of these got a fresh per-turn budget. A repo's policy can also set a daily spend cap (`hangar repo set acme/app --max-usd-per-day 60`), and `HANGAR_PERSON_MAX_USD_PER_DAY` one per person across all their tokens; new jobs over either wait for approval, and follow-ups are refused. Days start at midnight in `HANGAR_BUDGET_DAY_TIMEZONE` (UTC unless set). [docs/repo-policy.md](docs/repo-policy.md#budgets)
- **No more stray `HANDOFF.md`.** The `repo-conventions` skill no longer asks agents to write it, and delivery keeps new agent scratch files (`HANDOFF.md`, `RESULT.md`, `NOTES.md` at the root, `*.orig`, `*.rej`) out of PRs unless the task names them.

### Work comes in from Jira and GitHub Projects

- **Jira and GitHub Projects intake.** An issue moved to a configured status (or given a label) in a mapped Jira project, or an issue moved to a configured column on an organization's GitHub Projects board, becomes a job (`HANGAR_JIRA`, `HANGAR_GITHUB_PROJECTS`). Jira comes in through an admin webhook (signed with its secret, `X-Hub-Signature`) or an Automation rule's web request, at `/api/hooks/jira`; project items through the GitHub webhook route. Hangar writes back as the job runs: a comment with a link when the agent starts, the agent's question (the job's person answers it in a comment), the outcome with the PR (a remote link in Jira), and a status transition or column move per stage. Jira Cloud and Data Center. The Jira credentials are control-plane only. A job belongs to the person the Jira account or GitHub user (by user id) is linked to, who is trusted, and only they continue it; an Automation request's body can't say who acted (hangar reads it from the issue's history); the issue's text always reaches the agent fenced as untrusted; an unlinked sender's job (a project-board mover not in `HANGAR_GITHUB_TRUSTED`) waits for a teammate's approval and runs on team credentials. [docs/intake.md](docs/intake.md)

### An approval lands the PR

- **An approval lands the PR, with the human gate kept.** Agent PRs come from a GitHub App (`HANGAR_GITHUB_APP_CREDENTIAL`), whose tokens are minted per repo with `contents` and `pull_requests` write only, so the person who asked can approve them; the gateway's App tokens drop to `contents: write`. With `land: auto_after_approval` in the repo policy, an approval of the PR's head by one of its `approvers` or a code owner, plus green required checks, makes the control plane arm auto-merge for exactly that commit (`expectedHeadOid`), or merge it with `sha` when it is already mergeable. Any push clears the approval and disarms, and no agent turn starts while armed. Jobs record `landing.pr_state` (open, approved, merged, closed), `merged_at` and the time from green checks to merged. A merged or closed PR ends the job's session (final checkpoint, then the sandbox goes), and schedules update their open PR instead of opening another. Each agent PR gets a review packet comment (verification and base-red, cost and budget, harness version and model, files, risk tier from `risk_paths`, session and demo links). `hangar doctor` warns when the branch protection lacks required reviews, stale-approval dismissal or approval of the latest push. A "needs you" inbox: `hangar://inbox`, `hangar inbox`, `GET /api/inbox`, per person, with PRs to review, agents' questions, approvals (agents' secret and egress requests among them) and failed jobs. **Upgrade note:** the webhook needs the `pull_request` event (`hangar doctor --fix`). [docs/landing.md](docs/landing.md)

### Environments that live with the repo

- **`.hangar/environment.yaml`: the repo describes its own environment.** `install` (idempotent, runs on every build), `start` (once per sandbox), `terminals` (long-running processes), `verify` and `extends`, committed next to the code. The file is untrusted. It is parsed strictly (no unknown fields, no YAML aliases, under 64 KiB) and read from the commit, never the working tree. It can't set what an admin decides (image, base, secrets, credentials, MCP servers, runtime class, resources), and a file that tries is refused with that reason. Per field, the job wins, then the file, then the repo's policy, then the environment. Environment specs take the same `install`, `start` and `terminals` fields. `hangar env check` and `POST /api/envbuilds/validate` validate a file without saving anything. [docs/environments.md](docs/environments.md)
- **Versioned builds: agents start with the dependencies installed.** A repo with an `install` gets builds: the environment's image, a clone of the default branch, then `install`, run in an ordinary sandbox under the environment's isolation. The checkout is kept as an image (`ADD`ed, no `RUN`), per provider (Docker and Kubernetes), keyed by the repo, the environment, the provider, the install, the lockfiles' git blob ids and the environment's image. Builds run only in the background: after a clone hangar notices the repo or the environment moved on, and startup's prebuild catches environment changes. A failed build never replaces the active one. Sandboxes fall back to the last good build, or to the environment's image with a warning at the top of the agent's instructions and in the job's events. `get_sandbox` shows `env_build` (version, fallback, stale, reason). Each repo keeps its last 5 builds (`hangar env builds`, `build-show`, `build-repo`); an admin can roll back, which pins until `hangar env unpin` (audited). Build secret ids the repo names reach the install command only, and the checkout is checked for their values before it is kept.
- **The supervisor: `hangar-agent svc`.** One command for the agent to see (`status`, `wait`, `logs`), start, stop and restart the environment's processes, or to add its own. It runs `start`, keeps `terminals` up (restart with backoff, readiness by port or command) and writes each one's output to `~/.hangar/svc/logs/`, where the agent can search it. It's a standard-library python3 script installed in each sandbox like `hangar-agent`, running as the agent's user. The agent's instructions get a "Your environment" section and a `hangar-environment` skill.
- **Services beside the sandbox.** `services: {postgres: {image: postgres:17, port: 5432}}` runs Postgres, Redis and the like as pod sidecars on Kubernetes, and on Docker as containers on an internal network of the sandbox's own. They share the sandbox's runtime and hardening (uid 1000, no capabilities), are reachable at their name, and are torn down with it. Images must match `HANGAR_ENV_SERVICE_IMAGES` (Docker's official images by default).
- **Preview ports.** `ports:` declares what the sandbox's owner may open in a browser: `hangar sb preview` (or `GET /api/sandboxes/{ref}/previews`) gives a two-minute link to `<port>-<sandbox>.<HANGAR_PREVIEW_DOMAIN>`, which signs that browser in to that origin only. Nothing is public. Only declared ports, owner-scoped, checked on every request, and the app never sees hangar's credentials. Off until `HANGAR_PREVIEW_DOMAIN` is set (`localhost` on a laptop).
- **Hangar's own repo has one:** [.hangar/environment.yaml](.hangar/environment.yaml).

### Every agent gets its own computer, and can diagnose its environment ([docs/computer-use.md](docs/computer-use.md))

- **`computer:` in an environment** adds a virtual display, a window manager, VNC on 127.0.0.1, ffmpeg and Chromium
  (Playwright 1.63.0) to the image. `hangar-agent screenshot`, `record start|stop` and `browse` hand screenshots and
  MP4 demos back as artifacts; they appear as session events and in the job's PR body, listed by name and fetched
  through hangar signed in (`HANGAR_PR_MEDIA_LINKS=signed` embeds them through expiring links anyone holding them
  can open; `HANGAR_PR_MEDIA_LINK_DAYS`). Works under gVisor (Chromium's own sandbox off, with gVisor as the
  boundary; a small `/dev/shm` handled), and says plainly what is missing where it can't run. `browser_mcp: true`
  adds Playwright's MCP server for every harness. Sandboxes with a computer get the `hangar-verify-ui` skill.
- **Watch or take over an agent's screen:** `hangar screen <job|session> [--control]` or `POST /api/screen/tickets`.
  One-time tickets, owner-scoped; view-only is enforced by hangar; no port is exposed; every view, takeover and
  disconnect is audited.
- **`hangar-agent env doctor`** and a `hangar-env` MCP server in every harness report the build version and
  whether it is a fallback, unhealthy services and ports, missing secret names, whether a host is reachable under the
  egress policy, and recent setup failures, from `~/.hangar/envstatus.json` (`HANGAR_ENV_DOCTOR_MCP`). Messages in it
  are redacted.
- **`hangar-agent env request secret NAME | egress HOST --why ...`** files a request with the owner: an elicitation in
  `wait_for_turn`, session and job events, the audit log, `hangar requests`, `/api/env-requests`, and in MCP
  `pending_approvals` and the inbox, answered with `answer_approval`. No new MCP tools. Never granted automatically, and rate
  limited (5 a turn, 5 waiting per session, 30 an hour per owner, no re-asking a denied target). Picked up while
  the turn runs (`HANGAR_ENV_REQUEST_POLL_SECONDS`, 30).
- **Job prompts ask for autonomy:** report blockers with `env request` and keep working on everything else.

### Enterprise IT for agents: egress, secrets, cloud credentials

- **Egress allowlists by hostname.** An environment's `egress.mode` is `open` (as before, and the default through `HANGAR_EGRESS_DEFAULT`), `allowlist` or `none`. Proxied sandboxes reach only the git gateway and hangar's egress proxy, with no DNS: a NetworkPolicy and the SandboxTemplate's own policy on GKE, an internal Docker network (`hangar-egress`) on a Linux host. The proxy runs beside the git gateway, never terminates TLS, and checks each connection's host, its SNI or `Host`, and the public address it resolves to. It allows the harness's own API hosts, presets (`packages`: PyPI, npm, crates, the Go proxy, GitHub), the environment's and repo policy's `allow`, and hosts an owner approved after `hangar-agent env request egress`. A repo policy can only tighten the mode. Denials are audited per sandbox and person and show up in the session; allowed traffic is audited per host every minute; `hangar_egress_*` metrics. E2B and Docker Desktop can't enforce it, so proxied environments don't start there. [docs/security.md](docs/security.md#egress-allowlists)
- **Secrets are scanned for before anything leaves.** Before hangar pushes a job's branch it scans every new commit's patch (a token added and deleted later still leaves with the push), the uncommitted and untracked change, and the commit messages. It looks for stored credential values and their encodings, and for GitHub, Slack, AWS, Google, Anthropic, OpenAI, npm, PyPI, GitLab, Stripe, Hugging Face, private-key and hangar token formats. A hit blocks the push. The agent gets a follow-up turn with each file and line (never the value) to remove it and rewrite the commits, up to `HANGAR_SECRET_SCAN_ROUNDS` (2); after that the job fails as `secret_found` with nothing pushed. A 60 MB change scans in about half a second. PR titles and bodies, GitHub and Slack comments, and text artifacts are masked; a binary artifact holding a stored value is withheld. `HANGAR_SECRET_SCAN=block|warn|off`. [docs/security.md](docs/security.md#secret-scanning)
- **Redaction catches encoded secrets** (hardening B4). `broker.redact` also masks stored values reversed, in hex, in base64 at any alignment (line-wrapped too) and percent-encoded, so `printf %s "$X" | rev` no longer prints a stored secret. The docs say plainly what redaction can't stop. [docs/security.md](docs/security.md#redaction)
- **Build secrets** reach only an environment's image build, never the running sandbox. An admin maps them in `build_secrets` on the environment or the repo policy; a repo's file can only name ids. They're passed as BuildKit secret mounts, with values never on a command line or in the build log, and install steps are checked for leftovers. [docs/security.md](docs/security.md#build-secrets)
- **Short-lived cloud credentials instead of stored keys.** An environment's `cloud:` (admin) makes hangar an OIDC issuer for its sandboxes. Each gets an RS256 ID token for one audience, valid `lifetime_minutes` (60), renewed only while the sandbox runs. Its subject is the environment that sets `cloud:` (`hangar:env:<name>`): grant on that, or on `person`, never on `repo`, which whoever starts a sandbox picks. For GCP, an `external_account` configuration lets Workload Identity Federation exchange it (`GOOGLE_APPLICATION_CREDENTIALS`, gcloud too). For AWS, `AWS_ROLE_ARN` and `AWS_WEB_IDENTITY_TOKEN_FILE` drive `AssumeRoleWithWebIdentity`. The keys are in the vault, with discovery at `/.well-known/openid-configuration`, JWKS at `/oidc/jwks.json` (uploadable to GCP, so hangar can stay private) and `POST /api/cloud/rotate` (old keys are unpublished 12 hours later, or at once with `drop_old`). [docs/security.md](docs/security.md#short-lived-cloud-credentials)
- **Egress closed further (Wave 3, egress2).** The proxy reads the whole ClientHello before relaying it and refuses Encrypted ClientHello (`encrypted_client_hello` 0xfe0d per RFC 9849, `ech_outer_extensions`, draft ESNI; GREASE too, so the computer image turns ECH off in Chromium), more or fewer than one server name, SSL 2/3 hellos, repeated extensions, and a second hello after a HelloRetryRequest that fails the same checks. With the git gateway configured, the `pypi`, `npm` and `go` presets read through hangar's **read-only package mirror** (`/pkg/<ecosystem>/` on the gateway: GET and HEAD only, no client credentials, so publish endpoints are unreachable by construction), with a disk cache, or Artifact Registry remote repositories on GKE (`HANGAR_PACKAGE_MIRRORS`); Go is served from the module proxy's cache only, so a module path can't make it fetch from an origin. `packages` no longer opens GitHub, and `crates` no longer opens crates.io (its publish API). Gateway-mode sandboxes read their own repo's REST API, read-only, at `$HANGAR_GITHUB_API` (`curl -n`). One person's sandboxes share `HANGAR_EGRESS_MAX_CONNECTIONS_PER_PERSON` (640) tunnels, and a restart lets open tunnels finish for `HANGAR_EGRESS_DRAIN_SECONDS` (20). The threat model now says which CDNs still allow domain fronting. [docs/security.md](docs/security.md#what-egress-doesnt-stop)
- **The agent's own pushes are scanned (Wave 3, egress2).** The git gateway advertises `no-thin`, holds each push (up to `HANGAR_GATEWAY_SCAN_MAX_MB`, 64), rebuilds the pack's objects and scans its commits, file names and new files with the delivery scan's patterns, in a worker thread, before any of it goes upstream. A hit refuses the push with `file:line` and the kind in git's output, never the value (`secret.found`, `source: gateway`); a hit already in the file the push builds on doesn't count. [docs/security.md](docs/security.md#the-agents-own-pushes)
- **Cloud tokens live an hour at most, and keys can rotate on a schedule (Wave 3, egress2).** `lifetime_minutes` is 5 to 60 (retired keys leave the JWKS an hour later), and `HANGAR_OIDC_KEY_ROTATION_DAYS` publishes the next signing key a week before it signs (`cloud.key.next`).

### Restarts, the power schedule and deploys

- **Restarts and the nightly power cycle strand nothing.** One reconciler, on a task of its own (`reconciler.py`), runs at startup and every `HANGAR_RECONCILE_INTERVAL_SECONDS` (30). A sandbox a restart left `pending`, `starting` or `stopping` is finished: a create is torn down and its exclusive lease freed at once (a Codex login was blocked for the sandbox's 4-hour TTL), a destroy is completed, and a create that never stored its provider ref is found by its label. On GKE the pod UID is recorded, so a pod that node repair or a scale-down recreated blank under the same claim counts as gone; its session resumes from its checkpoint, and envd's address is cached per pod. A destroy's provider steps run on a task of their own, so a cancelled caller no longer leaves a sandbox `stopping` forever. Each sandbox it acts on gets `failed_stage`, `cause` (`orphaned_by_restart`, `pod_replaced`, `gone`) and the create's `stages` in `info`.
- **Interrupted jobs resume instead of failing.** A job a restart caught mid-turn, whose session has a checkpoint, gets a follow-up turn that resumes from it; one caught provisioning starts over. Each does so at most `HANGAR_JOB_RESTART_RESUMES` (2) times, and they re-enter the queue `HANGAR_JOB_RESTART_STAGGER_SECONDS` (20) apart.
- **GitHub deliveries missed while hangar was down are redelivered.** At startup hangar asks GitHub to redeliver each failed delivery of the repos' webhooks since the last start, and a delivery is marked handled only after its handler returns, so one a dying pod half handled runs again.
- **`power.sh down` drains first.** `POST /api/admin/drain` holds queued jobs; the script waits for creates, destroys and suspends in flight, checkpoints the turns still running, and only then powers the sandbox pools down (hangar itself stays up: below).
- **Heartbeats for background loops:** `hangar_loop_last_tick_timestamp{loop}` and `hangar_loop_failures_total{loop}` for the reaper, reconciler, sessions, schedules and backups.
- **The control plane stays up overnight; only the sandbox pools power down.** `power.sh down` scales the `sandboxes-*` pools (gVisor, Kata, microVM) to 0 and leaves hangar and the system pool up: GitHub, Slack, Jira and GitHub Projects events are queued, jobs wait with `waiting: sandboxes power on at 10:00 EDT`, and creates (REST, MCP, E2B, sessions) answer at once with that time (REST `503` with `Retry-After`) instead of waiting for a node. A job turn the power-down cuts off resumes from its checkpoint at power-up. The microVM pool comes back at its fixed size instead of autoscaling 0–4. `hangar power` shows the state; `hangar power up` (`POST /api/admin/power/up`) runs the power-up job early. [docs/gke.md](docs/gke.md#6-sandbox-nodes-off-at-night-optional)
- **A warm start at 09:50.** The gVisor pool comes back at a warm floor (`sandbox_warm_nodes`, 1), the `hangar-prepull` DaemonSet pulls every image and pack `hangar images plan` lists onto it, and then queued jobs start and each environment's warm pool is sized from last week's creates in the 10:00 hour (`HANGAR_POWER_WARM_POOLS`, `HANGAR_POWER_WARM_MAX`). The acceptance script's `warmstart` check times a warm and a cold create; `power` checks the refusal while the pools are off.
- **Gated deploys: `.github/workflows/deploy.yml`.** By hand or on a `v*` tag: images and the control-plane image, the owner's approval (`production` environment), `kubectl set image`, the rollout, `gke.sh` with no kubectl in its checks, the tool-list diff and server version in the run summary, and a rollback to the image it replaced on any failure, a cancel included (a doctor check that was already failing is reported, not rolled back for). The deploy's secrets are `production` environment secrets, released only on approval, and its identity can only patch the `hangar` Deployment. It refuses while the sandbox pools are off unless forced, and records each deploy in hangar. [docs/upgrading.md](docs/upgrading.md#deploying-with-deployyml)
- **Operator view.** `hangar doctor`, `GET /api/overview` and MCP `fleet_overview` show the power state, the last deploy and its acceptance result, and whether the reaper, reconciler, session and schedule loops pass on time. No new MCP tools.

### MCP

- **No MCP tool dies with its client, and every one answers within the budget.** `create_sandbox`, `create_sandboxes`, `fork_sandbox` and `build_environment` answer within `HANGAR_MCP_TOOL_WAIT_SECONDS` (150 s). Past that they return the sandbox or build as it stands (`starting`, with a `stage` saying what it waits on) and keep going in the background. Before, an MCP client that gave up on the call (claude.ai stops after about 230 s) cancelled the create, and the sandbox ended in `error`. Destroy, pause, resume, extend, snapshot, `fork_session` and `run_agent` now run on their own task like create, and answer with the work as it stands after `HANGAR_MCP_TOOL_WAIT_SECONDS`. `wait_for_turn` (300 s by default before), `exec`'s `timeout`, `process` `attach` and `terminal_send` waits are capped at it. A test calls every tool against a provider that never answers and fails on any that outlives the budget, so a new tool can't reintroduce the bug. `create_sandboxes`, which the first half of this broke, works again.
- **`build_environment` called again returns the running build** instead of queueing a second job with an empty log (and, with `force`, a second Cloud Build).
- **Stale tool lists are called out.** `serverInfo.version` is `<package>+tools.<hash of the tool list>` instead of `0.1.0`. The claude.ai apps never refetch the tool list, so a call from a client working from an older one gets a line asking to remove and re-add the connector (at most hourly), and an unknown tool's error says the same.
- **`hangar sb exec box -- cmd 'a b'` keeps its quoting** (`shlex.join`); a single argument is still a shell line.
- **An `mcp` acceptance check:** `create_sandbox` over MCP on a multi-harness environment within claude.ai's 230 s, a create whose client drops still comes up, then `exec`; no kubectl needed.

### Images and packs

- **Images and packs are built before anyone waits, and harness versions are pinned.** `hangar images plan` lists every environment image and harness pack tag the code needs on a provider and which the registry lacks (one HTTP request per tag, no `gcloud` process); `hangar images build` builds and pushes them. CI runs it on every push to main (`.github/workflows/images.yml`, Workload Identity Federation; it skips cleanly until the secrets exist) and `deploy/gke/up.sh` before rollout. `src/hangar/harnesses.lock.yaml` pins every harness (Claude Code 2.1.296 and Antigravity 1.3.3 by vendor checksum, no longer "latest"). A pack build fails unless the CLI reports the locked version, and records what it reported: `list_environments` (`harness_versions`), `hangar pack list` and every turn (`harness_version`) show it. Packs are mounted by digest (`repo@sha256:...`), and `hangar pack publish` no longer overwrites an existing tag without `--force`. In the cluster, image checks ask the registry over HTTP instead of spawning `gcloud`. **Every pack tag changes once with this release**: let CI (or `up.sh`) build them before rollout. [docs/gke.md §3](docs/gke.md#3-environment-images).
- **Harness packs hold the vendor's files, not hangar's launch glue.** Codex's pack has no wrapper script any more: `bin/codex` links to the vendor binary, and hangar adds the bundled `rg` to `PATH` when it sets up the sandbox. A change to how hangar starts a harness no longer changes a pack's digest, which is how #69 forced a Codex rebuild. pi's and Gemini's launchers name their prefix instead of finding it through `dirname` and `readlink` on the agent's `PATH` (harness review B5). This ships in the same release as the pinned harnesses above, so pack digests change once.
- **A create waits only on its own harness's pack.** Packs for the environment's other harnesses are mounted when they're already built. A stale one, after an upgrade changed that harness, is rebuilt in the background instead of holding up the sandbox. This is why the first `python` sandbox after the #69 upgrade took minutes: it rebuilt the Codex pack for a Claude Code sandbox. The image build a create triggers (first use, or an environment change) also builds just that harness's pack, side by side with the image. Scheduled warm-pool syncs never wait on a build. At startup, packs whose harness changed in the upgrade are rebuilt in the background. A create that does wait on its own pack says so in `stage`, with the time so far.

### Review fixes: trust, dedupe and restarts (Wave 3)

- **An auto-fix review round needs a reviewer the job's person or the repo trusts** (#91's open finding). A round runs with the job's person's login, so on a person's job only their linked account, an admin's, the repo policy's `approvers` or a code owner of every touched path starts one; a team job also takes anyone the GitHub front door trusts. Bots and hangar's own App never do. Every reviewer's text is now an untrusted attachment, each comment fenced and labelled with its author; the instruction is hangar's. Rule 6 in [docs/team.md](docs/team.md#who-is-trusted). **Upgrade note:** a collaborator who isn't linked, an approver or a code owner no longer starts rounds on members' jobs.
- **Slack events are marked handled after they are** (commit after handle, as #84 did for GitHub): a Slack retry of an event a dying process acknowledged but never handled now runs.
- **A restart or a lost sandbox during the base check provisions again and checks the base again** (#82), through #84's restart path, instead of resuming without a baseline (so the base's own failures failed the job) or failing.
- **A Jira delivery over 1 MB is audited (`jira.too_large`) and answered on its issue** (#92): when authentic and its issue waits for an agent, hangar comments once a day that the description is too large. It was dropped without a word.
- **Missed GitHub Projects deliveries are redelivered at startup** (#92): the startup pass also covers each `HANGAR_GITHUB_PROJECTS` organization's webhook (`projects_v2_item`), with the organization's Webhooks read and write permission.
- **Best-of-N attempts the power-down cuts off resume at power-up** (#95), each from its own checkpoint, instead of each failing (`sandbox_gone`).
- **Auto-merge is armed only when the base branch dismisses stale approvals** (#96 finding 7). Otherwise, or when hangar can't read the protection, it doesn't arm and `hangar doctor` fails with the fix; `hangar repo set owner/repo --no-require-stale-dismissal` opts a repo out.

## The overnight stack (#48–#69)

Twenty-one feature PRs (#48–#66, #68, #69) on top of `2e3e0a3` (main after #43), and the upgrade guide and acceptance script (#67). Upgrading a running hangar: [docs/upgrading.md](docs/upgrading.md), which lists every default that changes. Proving it on GKE: `bash scripts/acceptance/gke.sh`.

### Agents and sessions
- **Live turns: steer, interrupt and tool approvals** for Claude Code and Codex. A small driver runs the turn inside the sandbox. Approvals (`auto`, `ask` or `deny-risky`) reach MCP clients as elicitations, and are also available over REST and the CLI. [docs/steering.md](docs/steering.md). #59
- **The uid split.** On Docker, a turn's driver runs as hangar's own user and the agent as the sandbox user, so code the agent runs can't reach the driver, its key or its control files. GKE and E2B keep one user (`HANGAR_UID_SPLIT`). #66
- **Hangar-owned harness settings.** In a split sandbox, an `ask` or `deny-risky` turn starts its harness from the pack or bake, with hangar's copy of the environment and settings hangar writes, so the agent can't set up a later turn that never asks. The repository's `.claude` settings, `.mcp.json` and skills don't apply there; the environment's settings, MCP servers and instructions and the repository's CLAUDE.md do. Every split harness runs with `no_new_privs`. Hangar reads a split run's status, log and approvals from its own files. `HANGAR_UID_SPLIT=required` also covers `deny-risky`. Codex's pack changes, so republish it. [docs/steering.md](docs/steering.md#hangar-owned-harness-settings). #69
- **Verify inside the turn.** A job's `verify` runs before the agent stops: a Claude Code Stop hook, the driver for Codex, a follow-up turn for the others. Edited test files make the PR a draft. [docs/jobs.md §7](docs/jobs.md). #65
- **PR auto-fix.** Failing CI and trusted reviewers' comments on hangar's own PRs start follow-up turns, with round limits and a cooldown (`HANGAR_GITHUB_AUTOFIX`). The webhook needs new events. #65
- **Prompt caching.** A TTL policy per session or environment (`auto`, `5m`, `1h`, `off`), one model per session (a switch is warned about), best-of-N and fork siblings sharing the first one's cached prefix, and cache savings in usage. #63
- **Faster checkpoints and resume** (about 2x), with unchanged parts copied inside the store. A turn's end is noticed in about 0.2 s, and there are benchmarks under `scripts/bench/`. #53
- **Durable sessions.** Forks copy checkpoints inside the store instead of through memory. A checkpoint survives an agent that deleted its checkout. The usage of deleted sessions is kept. #57
- **Live turn events.** A running turn's log is followed through hangar-envd, so events reach readers in tens of milliseconds on Docker instead of up to a 5 s poll later. Session and job events stream over SSE (`Last-Event-ID` resumes) and MCP subscriptions. [docs/streaming.md](docs/streaming.md). #68
- **The seams between features.** 14 bugs fixed where best-of-N, budgets, `needs_input`, forks, triggers, Slack, A2A and the gateway meet. Best-of-N attempts and the judge are budgeted, and each job has one event stream. #49

### Sandboxes and providers
- **hangar-envd**, a Rust daemon in each Docker and Kubernetes sandbox. It speaks E2B's envd protocol and carries exec, files and terminals without a `docker exec` or pods/exec per call, falling back to those when it can't be reached. The control-plane image builds it. [docs/envd.md](docs/envd.md). #60
- **Streaming to clients.** `exec(stream=true)` sends output as MCP progress notifications, or as SSE over REST. A `process` tool runs background processes you can attach to, write to and kill, and directory watches arrive as resource updates. Every stream has caps per token and per stream, and ends on revocation, destroy, pause and shutdown. [docs/streaming.md](docs/streaming.md). #68
- **E2B-compatible API** at `/e2b`, with a sandbox router and a `sandboxes` token scope, so the stock `e2b` SDKs run on hangar sandboxes. [docs/e2b.md](docs/e2b.md). #61
- **A fast microVM tier.** The `e2b` provider drives E2B's cloud, self-hosted E2B or CubeSandbox (`HANGAR_E2B_FLAVOR`). Sandbox tiers (`fast`, `isolated`), hot resume from paused memory, and an optional nested-virtualization node pool in terraform. [docs/microvm.md](docs/microvm.md). #64
- **Isolation.** On Docker, sandboxes run on hangar's own network, where they can't reach each other, and the single-VM install blocks the metadata server. On GKE, NetworkPolicies give sandboxes an egress baseline and block ingress to them (`deploy/k8s/sandbox-network.yaml`). #48, #62

### Security and front doors
- **Front-door review.** Authorization gaps closed across GitHub, Slack, A2A, REST scopes, OAuth and MCP. Rate limits and caps per caller and per front door, replay protection for signed webhooks and Slack, refusal audits, Slack Connect members gated, and a stricter OAuth redirect policy with an RFC 8707 audience check. #50
- **Git gateway and session pull** hardened against a compromised sandbox: safe extraction of `session pull` archives, the `push-options` capability, reserved session branches, a deadline on the command list, and per-grant and per-source limits. #48
- **Every read of a sandbox-written file is capped.** Body caps follow the token's scope, replay entries are synced to disk, and Cursor's OAuth sign-in works by default. #56
